# Inyak Planner 교육과정 점검 및 업데이트 설명서

## 1. 문서 목적과 전체 작업 흐름

### 1.1 문서 목적

이 문서는 Inyak Planner에 이미 등록되어 있는 학번별 교육과정을 실제 수강편람 개설 이력과 대조하여 점검하고, 이후 발생한 교육과정 변경사항을 안전하게 반영하기 위한 유지보수 절차를 정리한 문서이다.

새로운 학번의 교육과정을 처음 구축하는 방법보다는, 이미 존재하는 `curriculum_YYYY.csv`를 대상으로 다음 작업을 수행하는 데 초점을 둔다.

- 교육과정 seed와 실제 개설 이력의 차이 확인
- 단순 데이터 오류와 실제 교육과정 변경의 구분
- 과목의 학점, 이수구분, 권장학년, 학기 변경 추적
- 과목 통합, 분리, 대체 등 구조적 변경 추적
- 신규 과목 추가
- 변경사항을 SQLite, 개발 PostgreSQL, 운영 PostgreSQL에 순차적으로 반영
- 기존 사용자 수강기록과 연결된 `curriculum_courses.id` 보존
- 웹의 교육과정 및 변경내역 화면에서 최종 결과 확인

교육과정 데이터는 단순히 가장 최신 학년도의 수강편람을 복사하여 갱신하지 않는다.

각 입학 학번이 실제로 해당 학년에 재학한 시점의 개설 이력을 기준으로 변경사항을 판단해야 한다. 따라서 동일한 과목이라도 입학 학번에 따라 현재 교육과정으로 반영해야 할 상태가 달라질 수 있다.

이 원칙은 이 문서 전체에서 가장 중요하다.


### 1.2 관리 대상 데이터

교육과정 유지보수 과정에서는 크게 두 종류의 데이터를 비교한다.

#### 교육과정 seed

`data/seed/curriculum_YYYY.csv`

각 입학 학번의 교육과정 상태와 변경 이력을 저장한다.

예:

    data/seed/curriculum_2022.csv
    data/seed/curriculum_2023.csv
    data/seed/curriculum_2024.csv

이 파일이 `curriculum_courses` 테이블의 기준 데이터가 된다.


#### 실제 개설 이력

수강편람 크롤링으로 수집된 `courses` 데이터를 사용한다.

이 데이터에는 연도별, 학기별 실제 개설 과목의 다음 정보가 포함된다.

- 학정번호
- 과목명
- 이수구분
- 학점
- 권장학년
- 개설 학기

교육과정 seed는 공식 교육과정을 표현하고, `courses`는 실제로 그 시점에 어떤 과목이 개설되었는지를 보여준다.

두 데이터의 차이를 자동으로 비교하는 것이 교육과정 audit의 기본 역할이다.


### 1.3 전체 작업 원칙

교육과정 변경 작업에서는 다음 원칙을 지킨다.

1. **최신 `dev` 브랜치를 기준으로 작업한다.**

   작업을 시작하기 전에 반드시 최신 GitHub `dev`의 seed와 관련 스크립트를 확인한다.

2. **Audit 결과만 보고 자동으로 교육과정을 수정하지 않는다.**

   Audit은 차이를 발견하는 도구이다.

   발견된 차이가 실제 교육과정 변경인지, 단순 오입력인지, 개설되지 않은 선택과목인지 사람이 판단해야 한다.

3. **입학 학번의 실제 재학연도를 기준으로 판단한다.**

   예를 들어 2022학번의 경우 일반적인 정상 진급을 기준으로 다음과 같이 대응한다.

       2022 → 1학년
       2023 → 2학년
       2024 → 3학년
       2025 → 4학년
       2026 → 5학년

   따라서 2022학번의 4학년 교육과정을 검증할 때는 2026년의 4학년 개설이 아니라 **2025년의 4학년 개설 이력**을 우선해서 본다.

4. **단순 오류 수정과 교육과정 변경 이력을 구분한다.**

   원래 seed 자체가 잘못 입력된 경우에는 값을 바로 고친다.

   반면 실제 교육과정이 시간이 지나면서 변경된 경우에는 `previous_*` 또는 `change_*` 필드를 사용하여 과거 상태를 보존한다.

5. **기존 행의 ID를 가능한 한 유지한다.**

   `curriculum_courses.id`는 사용자 수강이력에서 참조될 수 있으므로 PostgreSQL 반영 시 기존 행을 무조건 삭제 후 재삽입해서는 안 된다.

6. **개발 DB를 먼저 검증하고 운영 DB에 반영한다.**

   Production DB에 바로 쓰지 않는다.

7. **PostgreSQL import 전에는 항상 dry-run을 수행한다.**

   특히 다음 값을 확인한다.

       UPDATE
       INSERT
       DELETE

   예상하지 못한 `DELETE`가 발생한다면 실제 반영을 중단하고 원인을 먼저 확인한다.


### 1.4 전체 작업 흐름

한 학번의 교육과정 점검은 기본적으로 다음 순서로 진행한다.

    최신 dev 확인
        ↓
    현재 seed 상태 확인
        ↓
    audit 실행
        ↓
    차이점 분류
        ↓
    필요한 실제 개설 이력 추가 조사
        ↓
    변경 유형 확정
        ↓
    seed CSV 수정
        ↓
    audit 재실행
        ↓
    SQLite import
        ↓
    SQLite 검증
        ↓
    Git diff 확인
        ↓
    dev에 commit / push
        ↓
    개발 PostgreSQL dry-run
        ↓
    개발 PostgreSQL apply
        ↓
    개발 DB SQL 검증
        ↓
    개발 웹 화면 확인
        ↓
    운영 PostgreSQL dry-run
        ↓
    운영 PostgreSQL apply
        ↓
    운영 DB 최종 검증

중간 단계에서 문제가 발견되면 다음 단계로 넘어가지 않는다.

특히 아래 세 지점은 반드시 확인하고 진행한다.

    seed 수정 후 audit
    개발 DB 반영 전 dry-run
    운영 DB 반영 전 dry-run


### 1.5 완료 기준

한 학번의 교육과정 유지보수 작업은 다음 조건을 만족했을 때 완료된 것으로 본다.

- seed CSV가 의도한 현재 교육과정과 변경 이력을 표현함
- audit에서 새로 설명되지 않는 mismatch가 없음
- 실제 개설 이력에서 교육과정으로의 역방향 검증 결과가 정상임
- SQLite import가 정상 완료됨
- current / legacy / attribute change 수가 예상과 일치함
- 개발 PostgreSQL 반영 및 검증 완료
- 개발 웹에서 교육과정과 변경사항이 정상 렌더링됨
- 운영 PostgreSQL dry-run 결과가 예상과 일치함
- 운영 PostgreSQL 반영 후 최종 SQL 검증 완료

단, `NOT_FOUND`가 존재한다는 이유만으로 작업 실패로 판단하지 않는다.

과거 과목인 `legacy` 행, 아직 해당 학번이 도달하지 않은 학년의 과목, 실제로 개설되지 않은 전공선택 과목 등은 정방향 audit에서 `NOT_FOUND`로 남을 수 있다.

따라서 단순한 `NOT_FOUND` 개수보다 **각 항목의 이유가 설명 가능한지**와 **실제 개설 이력 → 교육과정 역방향 검증이 정상인지**를 더 중요하게 본다.


## 2. 교육과정 데이터 구조


### 2.1 기본 구조

학번별 전공 교육과정은 다음 seed CSV에 저장한다.

    data/seed/curriculum_YYYY.csv

예를 들어 2022학번의 교육과정은 다음 파일에 저장된다.

    data/seed/curriculum_2022.csv

이 seed는 단순히 현재 과목 목록만 저장하는 파일이 아니다.

하나의 파일 안에 다음 세 가지 정보를 함께 저장한다.

- 현재 적용되는 교육과정
- 과거 교육과정에서 변경되거나 폐지된 과목
- 동일 과목 또는 과목 구조가 어떻게 변경되었는지에 대한 변경 이력

따라서 한 학번의 CSV에는 현재 학생에게 적용되는 과목뿐 아니라 `legacy` 행이 함께 존재할 수 있다.


### 2.2 Seed CSV 컬럼

현재 교육과정 seed는 다음 19개 컬럼을 사용한다.

    entry_year
    grade
    semester
    course_name
    course_code
    completion_type
    credits
    notes
    change_group
    change_type
    change_role
    change_effective_year
    change_note
    previous_credits
    previous_completion_type
    previous_grade
    previous_semester
    attribute_change_effective_year
    attribute_change_note

이 컬럼들은 크게 네 그룹으로 나눌 수 있다.

1. 현재 과목 상태
2. 일반 메모
3. 구조적 변경 이력
4. 동일 과목의 속성 변경 이력


### 2.3 현재 과목 상태 필드

#### `entry_year`

해당 교육과정이 적용되는 입학 학번이다.

예:

    2022

`academic_year`와 혼동하지 않는다.

`entry_year = 2022`는 2022년에 개설된 과목이라는 의미가 아니라 **2022학번 학생에게 적용되는 교육과정**이라는 뜻이다.


#### `grade`

현재 교육과정에서 해당 과목이 배치되는 권장 학년이다.

예:

    3
    4
    5

과목이 실제 교육과정 변경으로 다른 학년으로 이동했다면 현재 위치를 `grade`에 기록하고 기존 위치는 `previous_grade`에 기록한다.


#### `semester`

현재 교육과정에서 해당 과목이 배치되는 학기이다.

일반적으로 다음 값을 사용한다.

    1
    2

과목이 다른 학기로 이동한 경우 현재 학기를 `semester`, 과거 학기를 `previous_semester`에 기록한다.


#### `course_name`

현재 또는 해당 행이 나타내는 과목명이다.

예:

    의약품합성학
    독성학1
    지역약국 예비실무실습

학정번호가 변경되면서 과목명이 함께 변경된 경우에는 `change_*` 구조변경으로 관리한다.


#### `course_code`

과목의 학정번호이다.

예:

    ADB046
    ADA198

현재 과목에는 가능한 한 실제 수강편람에서 사용하는 학정번호를 기록한다.

학정번호 자체가 변경된 경우 기존 코드를 덮어쓰는 것이 아니라 일반적으로 기존 행과 새 행을 `change_group`으로 연결한다.


#### `completion_type`

현재 이수구분이다.

주요 값:

    전필
    전선

동일 과목이 전선에서 전필 또는 전필에서 전선으로 변경되었다면 현재 값을 여기에 기록하고 과거 값은 `previous_completion_type`에 기록한다.


#### `credits`

현재 학점이다.

예:

    1
    2
    3

동일한 과목이 2학점에서 3학점으로 변경되었다면:

    credits = 3
    previous_credits = 2

와 같이 관리한다.


### 2.4 `notes`

`notes`는 해당 행 자체에 대한 일반적인 출처 또는 판단 근거를 기록하는 필드이다.

예:

    2022학년도 교육과정표 기준.
    2026학년도 실제 개설 이력 기준 현재 과목.
    2022학번이 5학년이던 2026학년도 1학기 실제 개설 이력에 따라 추가된 전공선택 과목.

`notes`와 변경 이력용 `change_note`, `attribute_change_note`를 구분해서 사용한다.

- `notes`
  - 해당 행 자체에 대한 설명
- `change_note`
  - 구조적 변경에 대한 설명
- `attribute_change_note`
  - 동일 과목의 속성 변경에 대한 설명


### 2.5 `change_*`: 구조적 변경 이력

`change_*` 필드는 과목의 정체성 또는 구조 자체가 변경되었을 때 사용한다.

대표적인 경우는 다음과 같다.

- 학정번호 변경
- 과목명 변경을 동반한 대체
- 하나의 과목이 여러 과목으로 분리
- 여러 과목이 하나의 과목으로 통합
- 여러 과목 간 복합적인 재편

사용 필드는 다음과 같다.

    change_group
    change_type
    change_role
    change_effective_year
    change_note


### 2.6 `change_group`

같은 구조변경에 속하는 과거 과목과 현재 과목을 하나의 그룹으로 묶는 식별자이다.

예:

    2022-SYNTHESIS
    2022-TOXICOLOGY
    2022-COMMUNITY-PRE-PRACTICE

같은 변경에 속한 모든 행은 동일한 `change_group` 값을 가진다.

예를 들어 과거의 두 과목이 하나의 과목으로 통합되었다면:

    ADB028 의약품합성학1  → legacy
    ADB038 의약품합성학2  → legacy
    ADA198 의약품합성학   → current

세 행 모두 동일한 `change_group`을 사용한다.

    2022-SYNTHESIS

`change_group` 이름은 DB의 특별한 enum 값이 아니라 사람이 알아볼 수 있도록 만든 식별자이다.

따라서 의미가 명확하고 학번 간 충돌이 없도록 다음 형태를 권장한다.

    학번-변경내용

예:

    2022-ANTICANCER
    2023-TOXICOLOGY


### 2.7 `change_type`

구조변경의 형태를 나타낸다.

현재 사용하는 주요 값은 다음과 같다.

    1:1
    1:N
    N:1
    N:M


#### `1:1`

하나의 기존 과목이 하나의 새 과목으로 변경된 경우이다.

예:

    ADB075 지역약국 예비실무실습
        ↓
    ADA115 지역약국 예비실무실습

학정번호만 변경되는 경우도 `1:1` 구조변경으로 관리할 수 있다.


#### `1:N`

하나의 기존 과목이 여러 개의 과목으로 분리된 경우이다.

예:

    ADB068 독성학
        ↓
    ADA234 독성학1
    ADA235 독성학2


#### `N:1`

여러 개의 기존 과목이 하나의 과목으로 통합된 경우이다.

예:

    ADB028 의약품합성학1
    ADB038 의약품합성학2
        ↓
    ADA198 의약품합성학


#### `N:M`

여러 기존 과목이 여러 새 과목으로 재구성되어 단순한 분리 또는 통합으로 표현하기 어려운 경우이다.

실제 적용 시에는 명확한 근거가 있을 때만 사용한다.


### 2.8 `change_role`

구조변경 그룹 안에서 각 행이 과거 상태인지 현재 상태인지를 나타낸다.

사용 값:

    legacy
    current


#### `legacy`

변경 전 교육과정에 존재했던 과목이다.

학생에게 현재 적용되는 교육과정에서는 더 이상 이 행을 현재 과목으로 취급하지 않지만, 변경 이력을 재구성하기 위해 행을 보존한다.


#### `current`

구조변경 이후 현재 적용되는 과목이다.

예:

    change_group = 2022-ANTICANCER
    change_type = 1:1

    ADB070 항암약물요법
        change_role = legacy

    ADB103 항암약물요법1
        change_role = current

구조변경이 없는 일반 과목에서도 importer 및 현재 데이터 구조에 따라 `current`가 사용될 수 있다.

핵심은 `legacy`가 명시된 행은 과거 상태이고, 현재 교육과정 합계를 계산할 때는 현재 과목과 구분해야 한다는 것이다.


### 2.9 `change_effective_year`

구조변경이 해당 학번의 교육과정에 실제로 적용된 연도를 기록한다.

여기서 매우 중요한 점은 **전체 대학 교육과정에서 그 과목이 최초로 등장한 연도와 반드시 같지 않다는 것**이다.

예를 들어 새 학정번호가 2024년부터 다른 학년에서 이미 사용되고 있었다고 하더라도, 2022학번 학생이 해당 변경을 실제로 적용받은 시점이 2026년이라면:

    change_effective_year = 2026

으로 기록할 수 있다.

즉 이 값 역시 학번별 cohort 관점에서 판단한다.


### 2.10 `change_note`

구조변경의 내용을 사람이 다시 보았을 때 이해할 수 있도록 설명한다.

예:

    2022학번 5학년 개설 기준 지역약국 예비실무실습의 학정번호가
    ADB075에서 ADA115로 변경됨.

또는:

    독성학이 2026학년도부터 독성학1과 독성학2로 분리되어 운영됨.

가능하면 다음 정보를 포함한다.

- 무엇이 변경되었는지
- 기존 과목이 무엇인지
- 현재 과목이 무엇인지
- 해당 학번에 언제 적용되었는지


### 2.11 `previous_*`: 동일 과목의 속성 변경 이력

`previous_*` 필드는 과목의 정체성은 유지되지만 일부 속성이 변경된 경우 사용한다.

사용 필드:

    previous_credits
    previous_completion_type
    previous_grade
    previous_semester
    attribute_change_effective_year
    attribute_change_note

대표적인 변경은 다음과 같다.

- 학점 변경
- 이수구분 변경
- 권장학년 변경
- 학기 변경

이 경우 기존 행을 `legacy`로 하나 더 만들지 않는다.

현재 상태를 기존 행에 기록하고, 변경 전 값만 `previous_*`에 보존한다.


### 2.12 `previous_credits`

학점 변경 전 값을 기록한다.

예:

과거:

    임상미생물학
    2학점

현재:

    임상미생물학
    3학점

seed에는 다음과 같이 기록한다.

    credits = 3
    previous_credits = 2

학점이 변경되지 않았다면 비워 둔다.


### 2.13 `previous_completion_type`

이수구분 변경 전 값을 기록한다.

예:

과거:

    의약화학1
    전선

현재:

    의약화학1
    전필

seed:

    completion_type = 전필
    previous_completion_type = 전선

변경되지 않았다면 비워 둔다.


### 2.14 `previous_grade`

권장학년 변경 전 값을 기록한다.

예:

과거:

    5학년 2학기

현재:

    4학년 2학기

이라면:

    grade = 4
    semester = 2
    previous_grade = 5

학기는 그대로이므로 `previous_semester`는 비워 둘 수 있다.


### 2.15 `previous_semester`

학기 변경 전 값을 기록한다.

예:

과거:

    4학년 1학기

현재:

    4학년 2학기

이라면:

    grade = 4
    semester = 2
    previous_semester = 1

학년은 변경되지 않았으므로 `previous_grade`는 비워 둔다.


### 2.16 여러 속성이 동시에 변경된 경우

한 과목에서 여러 속성이 동시에 변경될 수도 있다.

예를 들어:

    과거: 5학년 1학기 / 전선 / 2학점
    현재: 3학년 2학기 / 전필 / 1학점

이라면 다음과 같이 기록한다.

    grade = 3
    semester = 2
    completion_type = 전필
    credits = 1

    previous_grade = 5
    previous_semester = 1
    previous_completion_type = 전선
    previous_credits = 2

변경되지 않은 속성의 `previous_*` 필드는 비워 둔다.

즉 `previous_*`는 과거 행 전체를 복제하는 용도가 아니라 **실제로 변경된 속성만 기록하는 필드**이다.


### 2.17 `attribute_change_effective_year`

해당 속성 변경이 그 학번에 실제로 적용된 연도를 기록한다.

예:

2022학번의 `ADB046 임상미생물학`이 2025년 4학년 개설에서 2학점에서 3학점으로 변경된 경우:

    credits = 3
    previous_credits = 2
    attribute_change_effective_year = 2025

구조변경의 `change_effective_year`와 마찬가지로 학번별 실제 적용 시점을 기준으로 판단한다.


### 2.18 `attribute_change_note`

속성 변경의 내용을 기록한다.

예:

    2022학번 기준 임상미생물학이
    2025학년도 4학년 1학기 개설에서
    2학점에서 3학점으로 변경됨.

어떤 `previous_*` 값이 왜 존재하는지 나중에 다시 검토할 수 있을 정도로 작성한다.


### 2.19 `change_*`와 `previous_*`의 구분

두 종류의 변경 이력은 반드시 구분한다.

#### `previous_*`를 사용하는 경우

**같은 과목이라고 판단할 수 있고 학정번호도 유지되면서 속성만 변경된 경우**

예:

    ADB046 임상미생물학
    2학점 → 3학점

또는:

    ADB047 의약화학1
    전선 → 전필

또는:

    ADB050 건강기능식품학
    4-1 → 4-2


#### `change_*`를 사용하는 경우

**과목의 정체성 또는 구조 자체가 변경된 경우**

예:

    ADB075 → ADA115

또는:

    ADB068
        ↓
    ADA234 + ADA235

또는:

    ADB028 + ADB038
        ↓
    ADA198


판단 기준을 간단히 표현하면 다음과 같다.

    동일 과목 + 같은 학정번호 + 속성 변화
        → previous_*

    학정번호/과목 정체성/과목 수 자체의 변화
        → change_*


### 2.20 구조변경과 속성변경을 동시에 기록하지 않는 것을 기본으로 한다

구조변경 그룹에 들어간 `legacy` / `current` 행은 이미 과거와 현재 상태를 각각 별도의 행으로 가지고 있다.

따라서 일반적으로 구조변경에 따른 학년, 학기, 학점, 이수구분 차이를 다시 `previous_*`에 중복 기록하지 않는다.

예:

    ADB063
    4학년 1학기
    전선 2학점
        ↓
    ADA148
    5학년 2학기
    전선 2학점

이 경우 학정번호와 과목 정체성이 변경되었으므로 `1:1 change_group`으로 관리한다.

새 `ADA148` 행에 다시:

    previous_grade = 4
    previous_semester = 1

을 기록하지 않는다.

과거 상태는 이미 같은 `change_group`의 `legacy` 행인 ADB063에 존재하기 때문이다.


### 2.21 신규 과목

기존 교육과정에서 대응되는 과목이 없고 실제로 새롭게 추가된 과목이라면 구조변경으로 만들지 않는다.

예:

    ADA236 환경보건약학
    ADA239 약사와 건강증진

기존 과목과 대체 또는 분리·통합 관계가 없다면 일반 `current` 과목으로 추가한다.

이 경우:

    change_group
    change_type
    change_effective_year
    previous_*

등은 비워 둔다.

`notes`에는 해당 학번에서 실제로 확인된 개설 시점과 신규 추가 근거를 남기는 것이 좋다.


### 2.22 단순 데이터 오류는 변경 이력이 아니다

기존 seed 값이 애초에 잘못 입력되어 있었다면 이를 실제 교육과정 변경으로 기록하지 않는다.

예를 들어 공식 자료와 당시 실제 개설 이력을 모두 확인했을 때 처음부터 3학점이었던 과목이 seed에 실수로 2학점이라고 입력되어 있었다면:

    credits = 2
        ↓
    credits = 3

으로 바로 수정한다.

이 경우:

    previous_credits = 2

를 기록하지 않는다.

`previous_*`는 **우리 데이터가 잘못되어 있었던 역사**를 저장하기 위한 필드가 아니라, **실제 교육과정이 변경된 역사**를 저장하기 위한 필드이다.

이 구분을 하지 않으면 웹의 변경내역에 실제로 존재하지 않았던 교육과정 변경이 표시될 수 있다.


### 2.23 현재 교육과정의 의미

이 프로젝트에서 `current`는 단순히 "2026년 현재 대학에서 운영 중인 최신 교육과정"이라는 의미로 사용하지 않는다.

해당 `entry_year` 학생에게 지금까지 적용된 변경사항을 반영한 **그 학번의 현재 교육과정 상태**를 의미한다.

따라서 서로 다른 학번의 current 행은 같은 과목이라도 다음 값이 다를 수 있다.

- 학점
- 이수구분
- 권장학년
- 학기
- 학정번호
- 변경 이력

교육과정 유지보수 시 다른 학번의 current 값을 그대로 복사하지 않는 이유가 여기에 있다.


### 2.24 데이터 구조의 핵심 원칙

교육과정 seed를 수정할 때는 항상 다음 세 질문을 먼저 한다.

1. 이 값은 기존 seed의 단순 오류인가?
2. 같은 과목이 실제로 속성만 변경된 것인가?
3. 과목의 정체성 또는 구조 자체가 변경된 것인가?

이에 따라 처리 방법을 결정한다.

    단순 오류
        → 현재 값만 바로 수정

    동일 과목의 속성 변경
        → 현재 값 + previous_*

    구조적 변경
        → legacy/current + change_*

    완전히 새로운 과목
        → 새 current 행

이 분류가 교육과정 변경 이력 전체의 기반이 된다.


## 3. Audit 실행 및 결과 해석

### 3.1 Audit의 목적

교육과정 유지보수에서 audit은 교육과정 seed와 실제 수강편람 개설 이력을 비교하여 서로 맞지 않는 부분을 찾는 도구이다.

현재 사용하는 스크립트는 다음과 같다.

    scripts/audit_curriculum.py

이 스크립트는 다음 두 방향으로 검증한다.

    A. 교육과정 → 실제 개설 이력
    B. 실제 개설 이력 → 교육과정

두 방향을 모두 확인해야 한다.

정방향 검증만 하면 교육과정에 적혀 있는 과목이 실제로 어떻게 개설되었는지는 확인할 수 있지만, 실제로 새로 개설된 과목이 seed에 빠져 있는지는 놓칠 수 있다.

반대로 역방향 검증만 하면 실제 개설 과목의 미매핑은 찾을 수 있지만, 교육과정에 존재하면서 실제로 개설되지 않은 과목이나 과거 과목의 상태를 파악하기 어렵다.

따라서 audit 결과는 항상 A와 B를 함께 해석한다.


### 3.2 Audit이 사용하는 데이터

교육과정 쪽 데이터는 PostgreSQL의 `curriculum_courses`를 읽는 것이 아니라 다음 seed CSV를 직접 읽는다.

    data/seed/curriculum_YYYY.csv

실제 개설 이력은 SQLite의 다음 DB를 사용한다.

    data/db/inyak.db

그 안의 `courses` 테이블을 실제 개설 이력으로 사용한다.

따라서 seed를 수정한 직후에는 SQLite의 `curriculum_courses`를 다시 import하지 않았더라도 audit을 바로 실행할 수 있다.

반면 실제 개설 이력인 `courses`가 최신 상태가 아니라면 audit 결과 역시 최신 수강편람을 반영하지 못한다.

즉 audit 전에 반드시 다음 두 데이터가 올바른 상태인지 확인해야 한다.

- 검증하려는 학번의 최신 seed CSV
- 필요한 학년도·학기의 실제 수강편람이 들어 있는 `courses` 테이블


### 3.3 특정 학번 Audit 실행

일반적인 유지보수에서는 한 번에 하나의 학번을 검증한다.

프로젝트 루트에서 다음과 같이 실행한다.

    cd /Users/younyung.gene/inyak-planner

    python scripts/audit_curriculum.py \
      --entry-year 2022

예를 들어 2023학번은 다음과 같다.

    python scripts/audit_curriculum.py \
      --entry-year 2023

`--entry-year`를 생략하면 현재 존재하는 모든 `curriculum_*.csv`를 불러와 전체 학번을 검사한다.

    python scripts/audit_curriculum.py

교육과정 유지보수에서는 결과 해석이 복잡해질 수 있으므로 특별한 이유가 없다면 `--entry-year`를 지정하여 한 학번씩 검증하는 것을 권장한다.


### 3.4 Cohort 기준 연도 계산

Audit은 교육과정의 `entry_year`와 `grade`를 이용해 그 학생이 실제로 해당 학년에 재학했을 것으로 예상되는 연도를 계산한다.

계산식은 다음과 같다.

    실제 학년도 = 입학년도 + 권장학년 - 1

예를 들어:

    entry_year = 2022
    grade = 4

라면:

    2022 + 4 - 1 = 2025

이므로 2022학번의 4학년 과목은 2025학년도 실제 개설 이력과 비교한다.

반대로 실제 개설 이력에서 특정 연도의 과목을 검사할 때는 다음 식으로 해당 학번의 예상 학년을 계산한다.

    예상 학년 = 실제 학년도 - 입학년도 + 1

예:

    실제 학년도 = 2026
    입학년도 = 2022

이면:

    2026 - 2022 + 1 = 5

따라서 2026학년도 5학년 개설 과목만 2022학번의 5학년 교육과정과 비교 대상이 된다.

이 cohort filtering은 매우 중요하다.

예를 들어 2026학년도에 어떤 과목이 4학년에도 개설되어 있다고 해서 이를 2022학번의 4학년 교육과정과 바로 비교해서는 안 된다.

2022학번은 2026년에 5학년이기 때문이다.


### 3.5 A. 교육과정 → 실제 개설 이력

정방향 검증은 seed에 존재하는 각 과목에 대해 해당 학번이 그 학년에 재학했을 실제 연도와 학기의 `courses` 데이터를 찾는다.

기본 비교 키는 다음과 같다.

- 실제 학년도
- 학기
- 권장학년
- 학정번호

예를 들어 seed에 다음 과목이 있다고 가정한다.

    entry_year = 2022
    grade = 4
    semester = 1
    course_code = ADB046

Audit은 다음 실제 개설을 찾는다.

    academic_year = 2025
    semester = 1
    recommended_year = 4
    course_code = ADB046


### 3.6 `현재 검증 가능`과 `아직 검증 불가`

Audit은 먼저 해당 학년도와 학기의 실제 개설 데이터 자체가 SQLite에 존재하는지 확인한다.

예를 들어 어떤 학번의 6학년 2학기가 아직 미래이거나 아직 크롤링되지 않았다면 해당 과목은 검증할 수 없다.

결과에는 다음과 같이 표시된다.

    현재 검증 가능: 112
    아직 검증 불가: 9

`아직 검증 불가`는 오류가 아니다.

단순히 비교할 실제 수강편람 데이터가 아직 없다는 의미이다.

따라서 미래 학년이 포함된 학번의 경우 이 값이 0이 아니어도 정상이다.


### 3.7 `학점 일치`

학정번호, 학년, 학기 조건으로 실제 과목을 찾았고 실제 학점과 seed 학점이 같으면 학점 일치로 계산한다.

예:

    seed
    ADB046 / 3학점

    실제 개설
    ADB046 / 3학점

이 경우 별도의 상세 메시지는 출력하지 않고 최종 집계의 `학점 일치`에 포함된다.


### 3.8 `[CREDIT_MISMATCH]`

같은 학정번호가 기대한 학년·학기에 실제로 존재하지만 seed 학점과 실제 학점이 다른 경우이다.

예:

    [CREDIT_MISMATCH]
    ADB046 임상미생물학
    교육과정: 2.0
    실제: 3.0

이 결과만 보고 바로 seed를 3학점으로 덮어쓰면 안 된다.

다음 중 무엇인지 추가로 판단해야 한다.

1. seed가 처음부터 잘못 입력되어 있었는가?
2. 실제 교육과정에서 2학점 → 3학점으로 변경되었는가?
3. 다른 cohort용 개설을 잘못 비교하고 있는가?

실제 교육과정 변경이라면 `previous_credits`를 사용하고, 단순 데이터 오류라면 현재 값만 수정한다.


### 3.9 `[SECTION_CREDIT_CONFLICT]`

같은 학정번호, 같은 학년도, 같은 학기, 같은 권장학년으로 여러 분반이 존재하는데 서로 다른 학점이 기록되어 있는 경우이다.

예:

    실제 학점: [2.0, 3.0]

이 경우 audit은 어떤 값을 교육과정 학점으로 사용해야 하는지 자동 결정하지 않는다.

수강편람 원자료와 분반 내용을 직접 확인해야 한다.

이 상태에서는 seed를 수정하기 전에 실제 데이터 문제인지, 분반별로 정말 다른 학점이 운영된 것인지 먼저 조사한다.


### 3.10 `[NOT_FOUND]`

기대한 학년도, 학기, 권장학년, 학정번호 조합으로 실제 개설 과목을 찾지 못한 경우이다.

`NOT_FOUND`는 매우 중요한 조사 단서이지만 그 자체가 오류를 의미하지는 않는다.

Audit은 `NOT_FOUND`가 발생하면 추가 후보를 함께 보여준다.


#### 같은 학기 이름 기준 후보

같은 연도, 같은 학기, 같은 권장학년에 이름이 같거나 유사한 과목이 존재하는지 찾는다.

예:

    ADB075 지역약국 예비실무실습

을 찾지 못했는데:

    ADA115 지역약국 예비실무실습

이 존재한다면 학정번호 변경 가능성이 있다.


#### 같은 학년도 다른 학기 후보

같은 연도와 권장학년에서 같은 이름의 과목이 다른 학기에 개설되었는지 찾는다.

예:

    seed: 4-1
    실제: 4-2

라면 학기 이동 가능성이 있다.


#### 다른 권장학년 동일 학정번호 개설

같은 학년도에 같은 학정번호가 존재하지만 다른 권장학년으로 개설되었는지 확인한다.

예:

    seed: 5학년
    실제: 4학년

이라면 학년 이동 가능성이 있다.


### 3.11 `NOT_FOUND`를 해석할 때의 주의점

정방향 `NOT_FOUND`를 모두 0으로 만드는 것을 목표로 해서는 안 된다.

다음과 같은 행은 정상적으로 `NOT_FOUND`가 남을 수 있다.

#### Legacy 과목

구조변경 전 과목은 과거 상태 보존을 위해 seed에 남아 있지만 해당 cohort가 실제로 그 학년에 도달했을 때는 이미 새 과목으로 변경되어 있을 수 있다.

예:

    ADB075 지역약국 예비실무실습
        role = legacy

    ADA115 지역약국 예비실무실습
        role = current

이 경우 legacy인 ADB075가 `NOT_FOUND`로 나오는 것은 자연스럽다.


#### 실제로 개설되지 않은 전공선택 과목

교육과정표에는 존재하지만 해당 학년도에 실제 수강편람에 개설되지 않은 전선 과목일 수 있다.

이 경우도 seed에서 삭제해야 한다는 뜻은 아니다.


#### 아직 해석되지 않은 구조변경

같은 이름의 다른 학정번호 후보가 나온다면 구조변경 가능성을 조사해야 한다.

따라서 `NOT_FOUND`는 다음 두 그룹으로 나누어 생각한다.

    설명 가능한 NOT_FOUND
        → 유지 가능

    설명되지 않는 NOT_FOUND
        → 추가 조사 필요


### 3.12 정방향 결과 요약

정방향 결과의 마지막에는 다음과 같은 집계가 나온다.

    교육과정 과목 수
    현재 검증 가능
    아직 검증 불가
    학점 일치
    학점 불일치
    학정번호로 찾지 못함
    분반 간 학점 충돌

여기서 특히 우선적으로 조사할 것은 다음이다.

    학점 불일치 > 0
    분반 간 학점 충돌 > 0
    설명되지 않는 NOT_FOUND

단순히 `학정번호로 찾지 못함`의 숫자가 높다는 이유만으로 audit 실패로 판단하지 않는다.


### 3.13 B. 실제 개설 이력 → 교육과정

역방향 검증은 실제 `courses` 데이터에서 시작한다.

목적은 다음 질문에 답하는 것이다.

> 이 학번이 실제로 들었어야 할 학년의 개설 과목들이 교육과정 seed에 모두 설명되어 있는가?

이 검증은 특히 다음 항목을 찾는 데 중요하다.

- 신규 과목
- 학정번호 변경
- 학년 또는 학기 이동
- 학점 변경
- 이수구분 변경
- seed에서 완전히 빠진 과목


### 3.14 검사 대상 학정번호 Prefix

역방향 검증은 교육과정 seed에 존재하는 학정번호의 alphabet prefix를 수집하여 해당 계열의 실제 개설만 검사한다.

예를 들어 결과에 다음과 같이 표시될 수 있다.

    검사 학정번호 prefix: ADA, ADB

따라서 `courses` 테이블에 존재하는 모든 대학 과목을 검사하는 것이 아니라 해당 교육과정에서 사용하는 학정번호 계열을 대상으로 한다.


### 3.15 역방향 Cohort Filtering

실제 개설 이력이 있다고 해서 모든 학번과 비교하지 않는다.

예를 들어:

    2025학년도
    recommended_year = 4

인 실제 과목은 2025년에 4학년인 cohort와만 비교한다.

2022학번이라면:

    2025 - 2022 + 1 = 4

이므로 검사 대상이 된다.

반면 같은 2025학년도 과목이라도 3학년 개설이라면 2022학번의 역방향 검사 대상에서 제외된다.

이 때문에 audit 결과는 단순히 "최신 수강편람에 존재하는 과목"을 찾는 것이 아니라 **해당 학번이 실제로 그 시점에 맞닥뜨린 개설 이력**을 검사한다.


### 3.16 `교육과정 정확 대응`

다음 조건을 모두 만족하면 정확 대응으로 계산한다.

- 학번 일치
- 권장학년 일치
- 학기 일치
- 학정번호 일치
- 학점 일치
- 이수구분 일치

정상적으로 유지보수가 완료된 cohort는 가능하면 역방향에서 실제 개설 과목 대부분 또는 전부가 정확 대응으로 설명되어야 한다.


### 3.17 `[ATTRIBUTE_CHANGED_CANDIDATE]`

학정번호, 학년, 학기는 일치하지만 다음 속성 중 하나 이상이 다른 경우이다.

- 학점
- 이수구분

Audit 내부 비교 로직은 학년과 학기도 함께 비교할 수 있지만, 이 분류에 들어오는 시점에는 기본 위치가 이미 일치한 후보이다.

예:

    ADB046 임상미생물학

    seed:
    2학점

    실제:
    3학점

또는:

    ADB047 의약화학1

    seed:
    전선

    실제:
    전필

이 경우 동일 과목의 속성 변경 가능성이 높다.

하지만 반드시 실제 교육과정 변경인지 단순 seed 오류인지 조사한 뒤 결정한다.


### 3.18 `[TERM_OR_GRADE_MOVED_CANDIDATE]`

같은 학정번호가 seed에 존재하지만 실제 개설의 학년 또는 학기가 달라진 경우이다.

예:

    seed:
    ADB050 건강기능식품학
    4학년 1학기

    실제:
    ADB050 건강기능식품학
    4학년 2학기

또는:

    seed:
    5학년 2학기

    실제:
    4학년 2학기

이 경우 동일 과목이 이동한 것이라면 `previous_grade` 또는 `previous_semester`로 기록한다.

학점이나 이수구분도 함께 달라졌다면 해당 변경도 같이 검토한다.


### 3.19 `[CODE_CHANGED_CANDIDATE]`

실제 개설 과목과 동일한 이름의 과목이 같은 학년·학기에 seed에 존재하지만 학정번호가 다른 경우이다.

예:

    seed:
    ADB075 지역약국 예비실무실습

    실제:
    ADA115 지역약국 예비실무실습

이 경우 학정번호 변경 가능성이 높다.

보통 `1:1` 구조변경 후보가 된다.

다만 이름이 같다는 이유만으로 자동으로 같은 과목이라고 판단하지 않는다.

수강편람 이력과 과목 구조를 추가로 확인한다.


### 3.20 `[CODE_AND_POSITION_CHANGED_CANDIDATE]`

과목명은 동일하지만 학정번호뿐 아니라 학년 또는 학기도 달라진 경우이다.

예:

    seed:
    ADB071
    4학년 2학기
    호흡기계 및 소화기계 질환 약물치료학

    실제:
    ADA145
    5학년 1학기
    호흡기계 및 소화기계 질환 약물치료학

이 경우 단순 attribute change로 처리하지 않는다.

학정번호가 변경되었으므로 일반적으로 `1:1` 구조변경으로 관리하고 과거 위치는 legacy 행, 현재 위치는 current 행에 각각 보존한다.


### 3.21 `[UNMAPPED_OFFERING]`

해당 학년도에 그 cohort가 실제로 맞닥뜨린 개설 과목인데 seed에서 학정번호 또는 동일명 후보를 전혀 찾을 수 없는 경우이다.

예:

    [UNMAPPED_OFFERING]
    2026-2 ADA239 약사와 건강증진 2학점

이 경우 가장 먼저 다음 가능성을 검토한다.

1. 완전히 새롭게 추가된 과목
2. 기존 과목의 이름이 크게 변경된 경우
3. 분리 또는 통합된 과목
4. seed 누락
5. 실제 수강편람 데이터의 잘못된 권장학년

`UNMAPPED_OFFERING`은 신규 과목을 찾는 데 특히 중요하다.

다른 기존 과목과의 구조적 관계가 없다면 새 `current` 행으로 추가한다.


### 3.22 역방향 결과 요약

역방향 검증 마지막에는 다음 항목이 출력된다.

    검사 대상 실제 개설 과목
    교육과정 정확 대응
    속성 변경 후보
    학년/학기 이동 후보
    학정번호 변경 후보
    학정번호+위치 변경 후보
    교육과정 미매핑

교육과정 유지보수 전에는 여러 후보가 존재할 수 있다.

예:

    검사 대상 실제 개설 과목: 80
    교육과정 정확 대응: 48
    속성 변경 후보: 3
    학년/학기 이동 후보: 9
    학정번호 변경 후보: 6
    학정번호+위치 변경 후보: 2
    교육과정 미매핑: 12

각 후보를 조사하여 seed에 반영한 뒤 audit을 다시 실행한다.

정상적으로 정리된 뒤에는 다음과 같은 결과가 가능하다.

    검사 대상 실제 개설 과목: 80
    교육과정 정확 대응: 80
    속성 변경 후보: 0
    학년/학기 이동 후보: 0
    학정번호 변경 후보: 0
    학정번호+위치 변경 후보: 0
    교육과정 미매핑: 0


### 3.23 Audit 후보는 변경 유형을 확정하지 않는다

Audit 메시지의 이름에는 `CANDIDATE`가 붙는다.

이것은 의도적인 것이다.

예를 들어:

    [CODE_CHANGED_CANDIDATE]

가 나왔다고 해서 반드시 `1:1` 변경이라는 뜻은 아니다.

실제로는:

- 두 과목이 서로 관계없는 과목일 수도 있고
- 하나가 다른 과목으로 분리된 결과일 수도 있고
- 이름만 우연히 같은 과목일 수도 있고
- seed 자체의 학정번호가 잘못 입력된 것일 수도 있다

따라서 audit은 **후보 생성기**이고 최종 변경 유형은 사람이 확정한다.


### 3.24 Audit 결과 조사 순서

초기 audit을 실행한 뒤에는 다음 순서로 결과를 조사하는 것이 효율적이다.

1. `CREDIT_MISMATCH`
2. `SECTION_CREDIT_CONFLICT`
3. `ATTRIBUTE_CHANGED_CANDIDATE`
4. `TERM_OR_GRADE_MOVED_CANDIDATE`
5. `CODE_CHANGED_CANDIDATE`
6. `CODE_AND_POSITION_CHANGED_CANDIDATE`
7. `UNMAPPED_OFFERING`
8. 남아 있는 `NOT_FOUND`

특히 역방향 후보들은 실제 개설에서 발견된 변화이므로 우선적으로 조사한다.

`NOT_FOUND`는 legacy나 미개설 전선 과목이 포함될 수 있으므로 역방향 후보를 먼저 정리한 뒤 다시 보는 것이 좋다.


### 3.25 실제 개설 이력 추가 조사

Audit 결과만으로 변경 유형을 확정하기 어려운 경우 `courses` 테이블에서 해당 학정번호 또는 과목명의 연도별 개설 이력을 직접 확인한다.

조사 시에는 한 연도만 보지 말고 가능한 범위에서 여러 연도를 비교한다.

확인할 항목:

- `academic_year`
- `semester`
- `recommended_year`
- `course_code`
- `course_name`
- `completion_type`
- `credits`

예를 들어 학정번호 변경이 의심된다면 기존 코드와 새 코드 모두의 연도별 이력을 확인한다.

이를 통해 다음과 같은 흐름을 재구성할 수 있다.

    기존 학정번호
        ↓
    특정 연도부터 새 학정번호
        ↓
    해당 cohort가 실제로 새 코드를 적용받은 연도 확인

중요한 것은 전체 대학에서 최초로 변경된 연도와 해당 cohort에 실제 적용된 연도가 다를 수 있다는 점이다.


### 3.26 Seed 수정 후 반드시 Audit을 다시 실행한다

후보를 조사하고 seed를 수정했다고 해서 바로 DB import로 넘어가지 않는다.

같은 명령으로 audit을 다시 실행한다.

    python scripts/audit_curriculum.py \
      --entry-year 2022

수정 후에는 다음을 확인한다.

- 기존 `CREDIT_MISMATCH`가 해결되었는가
- 설명되지 않는 attribute 후보가 남아 있는가
- 이동 후보가 해결되었는가
- 학정번호 변경 후보가 해결되었는가
- `UNMAPPED_OFFERING`이 해결되었는가
- 새 수정 때문에 다른 후보가 생기지 않았는가
- 남은 `NOT_FOUND`가 모두 설명 가능한가

Audit이 다시 정상화되기 전에는 SQLite 및 PostgreSQL 반영 단계로 넘어가지 않는 것을 원칙으로 한다.


### 3.27 Audit 완료 판단 기준

Audit의 목표는 모든 숫자를 무조건 0으로 만드는 것이 아니다.

특히 정방향 `NOT_FOUND`는 정상적인 이유로 남을 수 있다.

실무적으로는 다음 상태를 목표로 한다.

#### 정방향

    학점 불일치 = 0
    분반 간 학점 충돌 = 0

그리고 남은 `NOT_FOUND` 각각이 설명 가능해야 한다.


#### 역방향

가능하면 다음 후보가 모두 해소된 상태를 목표로 한다.

    속성 변경 후보 = 0
    학년/학기 이동 후보 = 0
    학정번호 변경 후보 = 0
    학정번호+위치 변경 후보 = 0
    교육과정 미매핑 = 0

실제 개설 과목이 모두 정확 대응으로 설명되는 상태가 가장 이상적이다.


### 3.28 Audit에서 가장 중요한 원칙

Audit 결과를 읽을 때는 다음 순서를 기억한다.

    차이를 발견한다
        ↓
    실제 개설 이력을 조사한다
        ↓
    해당 cohort의 시점을 확인한다
        ↓
    단순 오류인지 실제 변경인지 판단한다
        ↓
    변경 유형을 결정한다
        ↓
    seed에 기록한다
        ↓
    audit을 다시 실행한다

즉 audit의 역할은 교육과정을 자동으로 만들어 주는 것이 아니라 **교육과정 변경을 놓치지 않도록 조사 대상을 체계적으로 드러내는 것**이다.




## 4. 교육과정 변경 유형 분류

### 4.1 변경 유형 분류의 목적

Audit에서 차이가 발견되면 바로 seed를 수정하지 않는다.

먼저 그 차이가 어떤 종류의 변화인지 분류해야 한다.

교육과정 유지보수에서는 크게 다음 네 가지로 나눈다.

    1. 단순 데이터 오류
    2. 동일 과목의 속성 변경
    3. 과목 구조 자체의 변경
    4. 완전히 새로운 과목

이 분류에 따라 seed에 기록하는 방식이 달라진다.

    단순 데이터 오류
        → 현재 값만 수정

    동일 과목의 속성 변경
        → previous_*

    구조적 변경
        → change_*

    신규 과목
        → 새 current 행

잘못 분류하면 웹의 변경내역이 실제 교육과정과 다르게 표시되거나, 과거 상태를 불필요하게 남기게 된다.


### 4.2 가장 먼저 확인할 질문

Audit 후보 하나를 볼 때는 다음 순서로 판단한다.

    1. 기존 seed 값이 처음부터 잘못된 것인가?
    2. 같은 과목이 실제로 속성만 바뀐 것인가?
    3. 학정번호 또는 과목 정체성이 바뀐 것인가?
    4. 하나의 과목이 여러 과목으로 분리되었는가?
    5. 여러 과목이 하나로 통합되었는가?
    6. 기존 과목과 관계없는 신규 과목인가?

필요하면 여러 연도의 실제 개설 이력을 확인해 이 흐름을 재구성한다.


### 4.3 단순 데이터 오류

기존 seed의 값이 공식 교육과정 또는 당시 실제 개설 이력과 처음부터 맞지 않았던 경우이다.

예:

    seed:
    2학점

    공식 교육과정:
    3학점

    당시 실제 개설:
    3학점

이 경우 2학점은 실제 과거 교육과정이 아니라 단순 입력 오류이다.

처리:

    credits = 3

으로 바로 수정한다.

다음과 같이 기록하면 안 된다.

    credits = 3
    previous_credits = 2

왜냐하면 실제로 2학점이었던 시기가 없기 때문이다.

`previous_*`는 데이터 수정 기록이 아니라 실제 교육과정 변경 이력을 저장하는 필드이다.


### 4.4 단순 오류로 판단하기 위한 근거

가능하면 다음 자료를 함께 본다.

- 해당 학번 공식 교육과정표
- 해당 cohort가 실제 수강한 연도의 수강편람
- 앞뒤 연도의 동일 과목 개설 이력
- Git history
- 이전 seed 작성 근거 또는 notes

특히 Git history에서 값이 최근 실수로 변경된 것이 확인된다면 실제 교육과정 변경으로 오인하지 않도록 주의한다.


### 4.5 동일 과목의 속성 변경

학정번호와 과목 정체성이 유지된 상태에서 다음 중 하나 이상이 변경된 경우이다.

- 학점
- 이수구분
- 학년
- 학기

이 경우 기존 행을 그대로 현재 행으로 사용하고 과거 값만 `previous_*`에 기록한다.


### 4.6 학점 변경

예:

    과거:
    ADB046 임상미생물학
    2학점

    현재:
    ADB046 임상미생물학
    3학점

처리:

    credits = 3
    previous_credits = 2
    attribute_change_effective_year = 2025

과목의 학정번호와 정체성이 유지되므로 별도의 legacy/current 구조를 만들지 않는다.


### 4.7 이수구분 변경

예:

    과거:
    ADB047 의약화학1
    전선

    현재:
    ADB047 의약화학1
    전필

처리:

    completion_type = 전필
    previous_completion_type = 전선

필요한 경우:

    attribute_change_effective_year = 2025

를 함께 기록한다.


### 4.8 학기 이동

예:

    과거:
    ADB050 건강기능식품학
    4학년 1학기

    현재:
    ADB050 건강기능식품학
    4학년 2학기

처리:

    grade = 4
    semester = 2
    previous_semester = 1

학년은 변하지 않았으므로 `previous_grade`는 비워 둔다.


### 4.9 학년 이동

예:

    과거:
    ADB082 심혈관계 질환 약물치료학
    5학년 2학기

    현재:
    ADB082 심혈관계 질환 약물치료학
    4학년 2학기

처리:

    grade = 4
    semester = 2
    previous_grade = 5

학기는 그대로이므로 `previous_semester`는 비워 둔다.


### 4.10 여러 속성의 동시 변경

하나의 과목이 동시에 여러 속성을 바꿀 수도 있다.

예:

    과거:
    5학년 1학기
    전선
    2학점

    현재:
    3학년 2학기
    전필
    1학점

처리:

    grade = 3
    semester = 2
    completion_type = 전필
    credits = 1

    previous_grade = 5
    previous_semester = 1
    previous_completion_type = 전선
    previous_credits = 2

변경된 속성만 `previous_*`에 넣는다.


### 4.11 1:1 구조변경

기존 한 과목이 하나의 새 과목으로 변경된 경우이다.

대표적인 형태:

- 학정번호 변경
- 과목명 변경
- 학정번호와 과목명 동시 변경
- 학정번호 변경과 함께 학년 또는 학기도 이동

예:

    ADB075 지역약국 예비실무실습
        ↓
    ADA115 지역약국 예비실무실습

처리:

    기존 ADB075
        change_role = legacy

    새 ADA115
        change_role = current

두 행은 같은:

    change_group
    change_type = 1:1
    change_effective_year

을 가진다.


### 4.12 학정번호 변경은 일반적으로 `previous_*`가 아니다

예:

    ADB075 → ADA115

처럼 학정번호 자체가 바뀌었다면 같은 과목 이름이라고 해도 별도 구조변경으로 관리하는 것을 기본으로 한다.

이유는 과거 학정번호와 현재 학정번호를 모두 보존해야 하기 때문이다.

따라서:

    previous_course_code

같은 별도 필드를 사용하는 대신 legacy/current 두 행으로 보존한다.


### 4.13 학정번호와 위치가 함께 변경된 경우

예:

    과거:
    ADB071
    4학년 2학기
    호흡기계 및 소화기계 질환 약물치료학

    현재:
    ADA145
    5학년 1학기
    호흡기계 및 소화기계 질환 약물치료학

처리:

    ADB071
        grade = 4
        semester = 2
        role = legacy

    ADA145
        grade = 5
        semester = 1
        role = current

이 경우 current 행에 다시:

    previous_grade = 4
    previous_semester = 2

를 기록하지 않는다.

과거 위치는 legacy 행이 이미 보존하고 있기 때문이다.


### 4.14 1:N 구조변경

하나의 과목이 둘 이상의 과목으로 분리된 경우이다.

예:

    ADB068 독성학
        ↓
    ADA234 독성학1
    ADA235 독성학2

처리:

    ADB068
        change_role = legacy

    ADA234
        change_role = current

    ADA235
        change_role = current

모든 행에 동일한:

    change_group = 2022-TOXICOLOGY
    change_type = 1:N

을 기록한다.


### 4.15 분리 여부 판단

과목 이름에 단순히 `1`, `2`가 붙었다는 이유만으로 1:N으로 판단해서는 안 된다.

다음 내용을 함께 확인한다.

- 기존 과목이 실제로 사라졌는가
- 새 과목들이 같은 교육 내용 계열인가
- 등장 시점이 연속적인가
- 해당 cohort에서 기존 과목 대신 새 과목들이 적용되는가
- 공식 교육과정 또는 실제 개설 흐름이 분리를 뒷받침하는가

관계가 불확실하다면 임의로 `change_group`을 만들지 않는다.


### 4.16 N:1 구조변경

여러 과목이 하나의 과목으로 통합된 경우이다.

예:

    ADB028 의약품합성학1
    ADB038 의약품합성학2
        ↓
    ADA198 의약품합성학

처리:

    ADB028
        role = legacy

    ADB038
        role = legacy

    ADA198
        role = current

모두 같은:

    change_group = 2022-SYNTHESIS
    change_type = N:1

을 사용한다.


### 4.17 통합 시 학점 합계가 같을 필요는 없다

과거 두 과목이 각각 2학점이었다고 해서 새 통합 과목이 반드시 4학점이어야 하는 것은 아니다.

실제 교육과정 개편으로 내용과 학점 구조가 함께 바뀔 수 있다.

따라서 통합 여부는 학점 합계만으로 판단하지 않는다.

실제 수강편람과 해당 cohort 적용 시점의 과목 구성을 기준으로 판단한다.


### 4.18 N:M 구조변경

여러 기존 과목이 여러 새 과목으로 재편된 경우이다.

예:

    A + B
        ↓
    C + D + E

단순한 1:N 또는 N:1로 표현하기 어렵고 여러 과목이 하나의 개편 단위로 움직였다는 근거가 있을 때 사용한다.

N:M은 가장 해석이 어려운 유형이므로 명확한 자료가 없으면 사용하지 않는 것이 좋다.


### 4.19 신규 과목

실제 개설 이력에는 존재하지만 기존 seed에서 대응되는 과목이 없고, 다른 기존 과목과의 대체·분리·통합 관계도 없는 경우이다.

예:

    ADA236 환경보건약학
    ADA239 약사와 건강증진

처리:

    새 current 행 추가

일반적으로 다음 필드는 비워 둔다.

    change_group
    change_type
    change_effective_year
    previous_credits
    previous_completion_type
    previous_grade
    previous_semester

`notes`에는 해당 학번이 실제로 이 과목을 적용받은 시점을 남긴다.


### 4.20 신규 과목과 구조변경의 구분

새로운 학정번호가 등장했다고 해서 무조건 신규 과목은 아니다.

다음 순서로 확인한다.

    새 학정번호 발견
        ↓
    같은 이름의 기존 과목이 있는가?
        ↓
    비슷한 이름의 기존 과목이 사라졌는가?
        ↓
    학점과 이수구분이 이어지는가?
        ↓
    같은 시기에 교체되었는가?
        ↓
    분리 또는 통합 관계가 있는가?

명확한 연결 관계가 있으면 구조변경으로 처리한다.

연결 근거가 없으면 신규 과목으로 처리한다.


### 4.21 이름이 달라도 같은 과목일 수 있다

구조변경 판단에서 과목명 일치는 강한 단서이지만 절대적인 기준은 아니다.

예를 들어 이름이 약간 바뀌거나 표현 방식이 변경될 수 있다.

반대로 이름이 같아도 실제로는 별개의 과목일 수 있다.

따라서 다음 정보를 종합한다.

- 학정번호 변화
- 등장 및 소멸 시점
- 학년
- 학기
- 학점
- 이수구분
- 주변 과목 구조
- 공식 교육과정 자료


### 4.22 이름 변경만 있는 경우

학정번호가 동일하고 과목명만 약간 변경된 경우는 상황에 따라 판단이 필요하다.

현재 데이터 모델에는 `previous_course_name` 필드가 없다.

따라서 단순 표기 변경인지 실제 과목 정체성 변경인지 먼저 판단한다.

#### 단순 표기 정정

예:

    띄어쓰기 수정
    오탈자 수정
    명백한 표기 통일

이 경우 현재 이름을 바로 수정하고 구조변경으로 남기지 않는다.


#### 실질적인 과목명 변경

학정번호는 같지만 과목의 공식 명칭이 실제 교육과정 개편으로 변경되었고 변경 이력을 웹에서 별도로 보여줄 필요가 있다면 현재 데이터 모델만으로는 표현 방식이 제한적이다.

이 경우 임의로 구조변경을 만들기 전에 데이터 모델 확장이 필요한지 먼저 검토한다.


### 4.23 같은 학정번호가 재사용되는 경우

같은 학정번호가 항상 같은 과목이라는 보장은 없다.

장기간의 개설 이력에서 동일 코드가 전혀 다른 과목명으로 재사용된 흔적이 있다면 단순 attribute change로 처리하면 안 된다.

이 경우:

- 연도별 과목명
- 학년
- 학기
- 학점
- 이수구분

을 확인해 실제 동일 과목인지 판단한다.

학정번호 일치는 강한 단서이지만 과목 정체성을 자동으로 보장하지 않는다.


### 4.24 과목이 사라졌다고 바로 legacy로 만들지 않는다

특정 연도 수강편람에서 과목이 보이지 않는다고 해서 바로 폐지 또는 구조변경으로 판단하지 않는다.

특히 전공선택 과목은 매년 개설되지 않을 수 있다.

다음 가능성을 먼저 확인한다.

- 해당 학기에만 미개설
- 격년 개설
- 교수 또는 학과 사정으로 일시 미개설
- 다른 학기로 이동
- 다른 학년으로 이동
- 학정번호 변경
- 실제 폐지

단순 미개설이라면 seed의 current 과목을 그대로 유지할 수 있다.


### 4.25 `change_effective_year` 판단

구조변경이 대학 전체에서 처음 발생한 연도보다 **해당 cohort에 실제 적용된 연도**를 우선한다.

예를 들어 ADA 계열 새 학정번호가 이미 2024년에 다른 학년에서 사용되고 있었더라도, 2022학번이 해당 과목을 실제로 수강해야 하는 시점이 2026년이었다면:

    change_effective_year = 2026

으로 기록할 수 있다.

이 기준을 사용해야 웹에서 해당 학번의 변경 시점을 자연스럽게 설명할 수 있다.


### 4.26 `attribute_change_effective_year` 판단

속성변경도 같은 원칙을 적용한다.

예:

    2022학번
    ADB046 임상미생물학
    4학년 과목

2022학번이 4학년이 되는 2025학년도에 실제 개설이 3학점이었다면:

    attribute_change_effective_year = 2025

로 기록한다.

다른 cohort가 더 일찍 같은 변경을 적용받았더라도 해당 학번의 실제 적용 시점을 기준으로 한다.


### 4.27 변경 이력과 현재 상태의 관계

Seed에는 변경 전 상태를 그대로 유지하면서 현재 상태를 별도로 계산하는 것이 아니라, 기본적으로 **현재 상태를 직접 저장**한다.

속성변경의 경우:

    현재 값
    +
    previous_*

구조변경의 경우:

    legacy 행
    +
    current 행

형태이다.

따라서 현재 교육과정 화면은 current 상태를 기준으로 구성하고, 변경내역 화면은 `previous_*`와 `change_*`를 이용하여 과거와 현재를 재구성한다.


### 4.28 변경 분류 예시 요약

#### Case A: 학점만 변경

    ADB046
    2학점 → 3학점

처리:

    previous_*


#### Case B: 이수구분 변경

    ADB047
    전선 → 전필

처리:

    previous_*


#### Case C: 학기 이동

    ADB050
    4-1 → 4-2

처리:

    previous_*


#### Case D: 학정번호 변경

    ADB075 → ADA115

처리:

    1:1 change_*


#### Case E: 학정번호와 위치 변경

    ADB071 4-2
        ↓
    ADA145 5-1

처리:

    1:1 change_*


#### Case F: 과목 분리

    ADB068
        ↓
    ADA234 + ADA235

처리:

    1:N change_*


#### Case G: 과목 통합

    ADB028 + ADB038
        ↓
    ADA198

처리:

    N:1 change_*


#### Case H: 완전히 새로운 과목

    ADA239 약사와 건강증진

처리:

    새 current 행


#### Case I: 기존 seed 오입력

    실제로 처음부터 3학점인데
    seed만 2학점

처리:

    현재 값 직접 수정
    변경 이력 없음


### 4.29 최종 분류 결정표

    기존 값이 잘못 입력됨
        → 단순 수정

    같은 학정번호, 같은 과목, 속성만 변경
        → previous_*

    학정번호 또는 과목 정체성 변경
        → 1:1 change_*

    한 과목이 여러 과목으로 분리
        → 1:N change_*

    여러 과목이 하나로 통합
        → N:1 change_*

    여러 과목이 여러 과목으로 재편
        → N:M change_*

    기존 과목과 대응 관계 없음
        → 신규 current


### 4.30 애매하면 기록하지 말고 추가 조사한다

변경 이력은 한번 DB와 웹에 반영되면 사용자에게 공식적인 교육과정 변화처럼 보인다.

따라서 근거가 불충분한 상태에서 임의로 다음을 만들지 않는다.

    previous_*
    change_group
    legacy
    current 관계

확신이 없으면 후보 상태로 남겨 두고 실제 개설 이력이나 공식 교육과정 자료를 추가 조사한다.

교육과정 유지보수에서 중요한 것은 모든 차이를 빠르게 없애는 것이 아니라, **실제로 확인된 변화만 정확하게 기록하는 것**이다.


## 5. 학번별 Cohort-Aware 검증 원칙

### 5.1 왜 Cohort-Aware 검증이 필요한가

교육과정 유지보수에서 가장 중요한 원칙 중 하나는 **같은 연도의 수강편람이라도 모든 학번에게 동일하게 적용되지 않는다는 점**이다.

대학의 교육과정은 여러 학번이 동시에 존재하는 상태에서 개편된다.

예를 들어 2026학년도에는 다음 학생들이 동시에 재학할 수 있다.

    2022학번 → 5학년
    2023학번 → 4학년
    2024학번 → 3학년
    2025학번 → 2학년
    2026학번 → 1학년

따라서 2026학년도 수강편람에서 4학년 과목으로 개설된 과목은 일반적으로 2023학번을 위한 실제 개설 상태를 보여준다.

2022학번의 4학년 교육과정을 검증할 때 이 값을 그대로 사용하면 안 된다.

2022학번이 실제로 4학년이었던 시점은 2025학년도이기 때문이다.


### 5.2 기본 계산식

정상적인 진급을 기준으로 학번과 실제 학년의 관계는 다음 식으로 계산한다.

    실제 학년도 = 입학년도 + 학년 - 1

예를 들어 2022학번의 경우:

    1학년 → 2022
    2학년 → 2023
    3학년 → 2024
    4학년 → 2025
    5학년 → 2026
    6학년 → 2027

따라서 `curriculum_2022.csv`의 3학년 과목을 실제 수강편람과 비교할 때는 2024학년도를 본다.

반대로 실제 개설 연도에서 특정 학번의 예상 학년을 계산할 때는 다음 식을 사용한다.

    예상 학년 = 실제 학년도 - 입학년도 + 1


### 5.3 Audit도 이 원칙을 사용한다

현재 `scripts/audit_curriculum.py`는 이 cohort 관계를 이용해 실제 개설 이력을 필터링한다.

예를 들어 다음 실제 개설이 있다고 가정한다.

    academic_year = 2026
    recommended_year = 5

2022학번에 대해서는:

    2026 - 2022 + 1 = 5

이므로 검사 대상이 된다.

반면:

    academic_year = 2026
    recommended_year = 4

인 과목은 2022학번의 검사 대상이 아니다.

2022학번은 2026년에 5학년이기 때문이다.


### 5.4 최신 수강편람을 그대로 복사하면 안 된다

교육과정 점검에서 가장 위험한 실수 중 하나는 **현재 최신 수강편람의 학년별 상태를 모든 과거 학번의 current 값으로 복사하는 것**이다.

예를 들어 어떤 과목이 다음과 같이 변화했다고 가정한다.

    2024년 3학년 개설: 2학점
    2025년 3학년 개설: 2학점
    2026년 3학년 개설: 3학점

2022학번은 2024년에 3학년이었다.

따라서 2022학번의 해당 과목 상태를 판단할 때 우선 적용되는 실제 개설은:

    2024년 3학년 / 2학점

이다.

2026년 3학년 개설이 3학점이라는 이유로 2022학번 값을 3학점으로 바꾸면 cohort를 섞는 오류가 발생한다.


### 5.5 실제 사례: 의약품합성학

2022학번의 의약품합성학은 cohort-aware 검증이 왜 필요한지를 잘 보여준다.

2026년 현재 수강편람만 보면 `ADA198 의약품합성학`이 3학점으로 운영되는 시점이 존재할 수 있다.

하지만 2022학번은 2024년에 3학년이었다.

2022학번이 실제로 이 과목을 적용받았던 시점의 개설은:

    2024학년도
    3학년
    2학기
    ADA198 의약품합성학
    2학점

이었다.

따라서 `curriculum_2022.csv`의 current 상태는 2022학번이 실제로 적용받은 2학점을 기준으로 잡았다.

즉:

    최신 상태 = 항상 해당 학번의 current 상태

가 아니다.


### 5.6 같은 과목이라도 학번별 current가 다를 수 있다

`current`는 대학 전체에서 가장 최신인 과목 상태를 뜻하지 않는다.

다음 의미에 가깝다.

> 해당 입학 학번이 지금까지 실제로 적용받은 교육과정 변경을 반영한 현재 상태

따라서 동일한 학정번호라도 학번에 따라 다음 값이 다를 수 있다.

- 학점
- 이수구분
- 학년
- 학기
- 변경 적용 연도
- 구조변경 여부

예를 들어:

    curriculum_2022.csv
    ADB050 건강기능식품학
    4-2

와:

    curriculum_2024.csv
    ADB050 건강기능식품학
    3학점

등이 서로 다른 변경 이력을 가질 수 있다.

한 학번에서 확인한 변경을 다른 학번에 자동 복사해서는 안 된다.


### 5.7 동일 연도에 여러 교육과정이 동시에 운영될 수 있다

교육과정 개편은 일반적으로 특정 신입생부터 적용되거나, 기존 재학생에게 일부 과목만 단계적으로 적용된다.

따라서 한 학년도에 다음 상황이 동시에 존재할 수 있다.

    저학년 → 신 교육과정
    고학년 → 구 교육과정
    일부 과목 → 공통 개편

이 때문에 같은 PDF나 수강편람 안에 구 교육과정과 신 교육과정의 흔적이 동시에 존재할 수 있다.

단순히 "2026학년도 자료"라는 이유만으로 모든 내용을 2026학번 교육과정으로 간주하거나, 반대로 모든 재학생에게 적용되는 것으로 간주해서는 안 된다.


### 5.8 공식 교육과정표와 실제 개설 이력의 역할

Cohort-aware 검증에서는 두 자료의 역할을 구분한다.

#### 공식 교육과정표

주로 다음을 판단하는 기준이다.

- 원래 해당 학번에게 배정된 과목
- 원래 권장학년 및 학기
- 원래 이수구분
- 원래 학점
- 교육과정 구조

#### 실제 수강편람

주로 다음을 확인하는 기준이다.

- 해당 cohort가 실제로 해당 학년에 도달했을 때 어떤 과목이 개설되었는가
- 학정번호가 변경되었는가
- 학점이 변경되었는가
- 이수구분이 변경되었는가
- 학년 또는 학기가 이동했는가
- 신규 과목이 추가되었는가

즉 공식 교육과정표는 출발점이고, 실제 개설 이력은 이후 변화 추적에 사용한다.


### 5.9 해당 학번이 실제로 만나지 않은 변경

어떤 과목이 대학 전체에서 변경되었더라도 해당 학번이 그 변경을 실제로 만나지 않았다면 그 학번의 이력에 반드시 기록해야 하는 것은 아니다.

예를 들어:

    2026년부터 3학년 과목 A가
    2학점 → 3학점으로 변경

되었다고 하자.

2022학번은 이미 2024년에 3학년을 마쳤다.

따라서 이 변경은 일반적으로 2022학번의 `previous_credits` 이력으로 기록하지 않는다.

반대로 2024학번이 2026년에 3학년이라면 이 변경은 2024학번에 직접 영향을 줄 수 있다.

같은 실제 개편이라도 학번마다 기록 여부가 달라질 수 있다.


### 5.10 과거에 시작된 변경이 나중 cohort에 적용되는 경우

반대 상황도 존재한다.

새 학정번호가 대학 전체에서는 이전부터 사용되고 있었지만 해당 학번이 그 과목을 수강해야 하는 학년에 도달한 것은 더 늦을 수 있다.

예를 들어 `ADA115 지역약국 예비실무실습`이 다른 cohort에서는 이미 이전 연도부터 사용되고 있었다고 하더라도, 2022학번이 해당 5학년 과목을 실제로 만난 시점이 2026년이라면:

    change_effective_year = 2026

으로 기록한다.

즉 `change_effective_year`는 다음 의미로 해석한다.

> 이 변화가 대학 전체에서 처음 발생한 연도

가 아니라:

> 이 변화가 해당 entry_year 교육과정에 실제로 적용된 것으로 판단한 연도


### 5.11 속성변경 적용 연도도 같은 방식이다

`attribute_change_effective_year`도 동일한 원칙을 사용한다.

예를 들어 어떤 과목의 대학 전체 변화가:

    2024년부터 2학점 → 3학점

이었다고 하더라도, 해당 cohort가 그 과목을 실제로 수강하는 학년이 2025년에 도달한다면 해당 학번에서는 실제 적용 시점을 2025년으로 기록할 수 있다.

중요한 것은:

    변화 자체의 최초 발생 시점

과:

    해당 cohort에 대한 적용 시점

을 구분하는 것이다.


### 5.12 학년 이동을 판단할 때의 주의점

같은 학정번호가 다른 권장학년에서 발견되었다고 해서 즉시 학년 이동으로 판단하지 않는다.

예를 들어:

    2025년
    ADB048 천연물의약품학
    3학년

이 발견되었는데 seed에는:

    4학년

이라고 되어 있다고 하자.

이 경우 먼저 해당 entry_year가 2025년에 몇 학년인지 확인한다.

2022학번이라면:

    2025 → 4학년

이므로 2025년 3학년 개설은 2022학번이 직접 적용받는 개설이라고 보기 어렵다.

다른 cohort용 신 교육과정일 가능성이 있다.

반면 2023학번이라면:

    2025 → 3학년

이므로 직접적인 변경 근거가 될 수 있다.


### 5.13 같은 학정번호가 여러 학년에서 동시에 존재하는 경우

일부 과목은 교육과정 전환기에 동일 학정번호가 여러 권장학년에서 동시에 개설될 수 있다.

예:

    2026
    4학년 ADBXXX
    5학년 ADBXXX

이 경우 단순히 학정번호만 보고 어느 행이 해당 cohort용인지 판단하면 안 된다.

반드시:

    entry_year
    academic_year
    recommended_year

의 관계를 함께 본다.


### 5.14 과목 분리·통합도 Cohort별로 판단한다

과목 분리 또는 통합 역시 대학 전체 변화만 보고 모든 학번에 복사하지 않는다.

예를 들어:

    독성학
        ↓
    독성학1 + 독성학2

라는 변화가 2026년에 발생했다면, 2026년에 해당 과목 학년에 도달한 cohort에게는 1:N 구조변경으로 기록할 수 있다.

하지만 이미 이전 연도에 기존 독성학을 수강한 학번이라면 같은 구조변경을 적용할 필요가 없을 수 있다.

따라서 구조변경도 항상:

    이 학번이 실제로 어느 버전을 적용받았는가?

를 먼저 본다.


### 5.15 신규 과목도 Cohort 기준으로 추가한다

`UNMAPPED_OFFERING`에서 새로운 과목이 발견되었다고 해서 모든 학번 seed에 추가해서는 안 된다.

예를 들어:

    2026학년도
    5학년
    ADA239 약사와 건강증진

이 새롭게 개설되었다면 2026년에 5학년인 2022학번에는 직접적인 신규 과목 후보이다.

반면 2023학번은 2026년에 4학년이므로 아직 이 과목을 실제로 적용받았다고 단정할 수 없다.

2023학번이 5학년이 되는 2027학년도 수강편람에서 이 과목이 계속 운영되는지 다시 확인해야 한다.


### 5.16 아직 미래인 학년은 확정하지 않는다

현재 실제 개설 이력이 없는 미래 학년의 과목은 audit에서 `아직 검증 불가`로 남을 수 있다.

예를 들어 2024학번의 경우 2026년에는 3학년이다.

따라서:

    4학년
    5학년
    6학년

실제 개설 이력은 아직 미래일 수 있다.

이때 최신 2026년 수강편람의 4·5·6학년 과목을 그대로 2024학번의 미래 current 상태로 가져오는 것은 위험하다.

그 과목들은 각각 다른 선배 cohort에게 적용되는 교육과정일 수 있기 때문이다.

미래 학년은 원래 공식 교육과정 seed 상태를 유지하고, 실제로 해당 cohort가 그 학년에 도달했을 때 다시 audit하는 것이 기본이다.


### 5.17 정상 진급 가정의 한계

현재 audit의 cohort 계산은 기본적으로 정상적인 연차 진행을 가정한다.

즉:

    입학년도 + 학년 - 1

공식을 사용한다.

이는 교육과정 자체의 적용 시점을 추적하기 위한 기준이다.

개별 학생의:

- 휴학
- 유급
- 복학
- 편입
- 조기졸업

등 개인 학적 상황을 반영하기 위한 계산은 아니다.

`curriculum_YYYY.csv`는 개별 사용자의 실제 재학 이력을 저장하는 파일이 아니라 **해당 입학 학번의 표준 교육과정**을 나타낸다.


### 5.18 편입생과 교육과정 cohort

Inyak Planner에서 실제 사용자가 편입생일 수 있더라도 교육과정 seed의 `entry_year`는 해당 교육과정 적용 학번을 기준으로 관리한다.

개별 편입생이 1·2학년 과정을 면제받거나 3학년부터 실제 학교생활을 시작하는 문제와, `curriculum_YYYY.csv`가 나타내는 학번별 교육과정 구조는 구분해서 생각한다.

Cohort-aware audit의 목적은 특정 학생 개인의 수강 시점을 계산하는 것이 아니라 **학번별 교육과정 변화가 어느 연도에 적용되었는지 추적하는 것**이다.


### 5.19 여러 연도의 이력을 보는 이유

한 연도만 보면 단순 미개설과 실제 변경을 구분하기 어려울 수 있다.

예:

    2024: ADBXXX 존재
    2025: 없음
    2026: ADBXXX 존재

이라면 2025년 미개설일 가능성이 있다.

반대로:

    2024: ADBXXX
    2025: ADAYYY
    2026: ADAYYY

이고 이름과 위치가 이어진다면 학정번호 변경 가능성이 높다.

따라서 구조변경 후보를 판단할 때는 가능하면 다음을 본다.

    변경 전 연도
    변화가 의심되는 연도
    변경 후 연도

단, 최종 seed에는 해당 cohort가 실제로 맞닥뜨린 상태를 기록한다.


### 5.20 다른 학번 seed는 참고자료이지 정답이 아니다

이미 정리된 다른 학번의 seed는 매우 유용한 참고자료이다.

예를 들어 2023학번에서:

    ADB068
        ↓
    ADA234 + ADA235

관계가 확인되어 있다면 2022학번의 독성학 변화 조사에도 강한 단서가 된다.

하지만 이를 그대로 복사해서는 안 된다.

확인해야 할 것은:

- 2022학번도 실제로 이 분리를 적용받았는가
- 적용 시점은 같은가
- 학점과 이수구분은 같은가
- 해당 cohort의 실제 개설은 무엇이었는가

이다.

따라서 다른 학번의 seed는 **변경 후보를 찾는 참고자료**로 사용하고, 각 cohort의 실제 이력으로 다시 검증한다.


### 5.21 Cohort-Aware 조사 절차

특정 audit 후보를 발견했을 때 다음 순서로 조사한다.

    1. 대상 entry_year 확인
        ↓
    2. seed의 grade 확인
        ↓
    3. 해당 학번이 그 학년이던 실제 연도 계산
        ↓
    4. 그 연도의 실제 수강편람 확인
        ↓
    5. 같은 코드 및 같은 이름의 앞뒤 연도 이력 확인
        ↓
    6. 다른 학년 개설이 다른 cohort용인지 구분
        ↓
    7. 해당 학번이 실제 적용받은 상태 결정
        ↓
    8. 단순 오류 / attribute / structural / 신규로 분류


### 5.22 적용 예시

#### 예시 1: 2022학번 4학년 과목

    entry_year = 2022
    grade = 4

계산:

    2022 + 4 - 1 = 2025

따라서 우선 확인:

    2025학년도
    recommended_year = 4


#### 예시 2: 2023학번 4학년 과목

    entry_year = 2023
    grade = 4

계산:

    2023 + 4 - 1 = 2026

따라서 우선 확인:

    2026학년도
    recommended_year = 4

같은 "4학년 교육과정"이어도 서로 다른 연도의 수강편람을 봐야 한다.


### 5.23 Cohort-Aware 판단 체크리스트

교육과정 값을 변경하기 전에 다음을 확인한다.

- 이 학번은 해당 연도에 실제로 몇 학년인가?
- 지금 보고 있는 수강편람의 `recommended_year`가 그 학년과 일치하는가?
- 최신 연도 자료를 과거 cohort에 잘못 적용하고 있지 않은가?
- 다른 학년의 동일 학정번호를 잘못 사용하고 있지 않은가?
- 다른 학번 seed에서 가져온 변경을 그대로 복사하고 있지 않은가?
- 해당 학번이 실제로 이 변경을 적용받았는가?
- `change_effective_year` 또는 `attribute_change_effective_year`가 해당 cohort의 실제 적용 시점을 나타내는가?


### 5.24 핵심 원칙

Cohort-aware 검증의 핵심은 다음 한 문장으로 정리할 수 있다.

> 교육과정 변경은 "현재 대학에서 이 과목이 어떻게 운영되는가"가 아니라, "이 입학 학번이 해당 학년에 도달했을 때 실제로 어떤 과목을 적용받았는가"를 기준으로 기록한다.

이 원칙을 지키지 않으면 서로 다른 학번의 교육과정이 섞이고, 과거 학생에게 미래 교육과정이 소급 적용되는 문제가 발생한다.

## 6. Seed CSV 수정 방법

### 6.1 수정 대상 파일

교육과정 유지보수에서 직접 수정하는 기본 파일은 다음과 같다.

    data/seed/curriculum_YYYY.csv

예:

    data/seed/curriculum_2022.csv

한 번의 작업에서는 가능하면 하나의 `entry_year`만 대상으로 한다.

현재 importer도 하나의 CSV 안에 여러 입학년도가 섞여 있으면 오류를 발생시키도록 되어 있다.


### 6.2 작업 전 최신 파일 확인

Seed를 수정하기 전에 반드시 최신 `dev` 브랜치의 파일 상태를 확인한다.

로컬에서 작업하는 경우 먼저:

    cd /Users/younyung.gene/inyak-planner

    git status
    git branch --show-current
    git pull --ff-only origin dev

등으로 현재 작업 상태를 확인한다.


### 6.3 CSV 헤더

현재 교육과정 변경 이력을 모두 지원하는 seed는 다음 19개 컬럼을 사용한다.

    entry_year
    grade
    semester
    course_name
    course_code
    completion_type
    credits
    notes
    change_group
    change_type
    change_role
    change_effective_year
    change_note
    previous_credits
    previous_completion_type
    previous_grade
    previous_semester
    attribute_change_effective_year
    attribute_change_note

기존 학번의 오래된 seed가 일부 변경 이력 컬럼을 가지고 있지 않다면 유지보수 과정에서 현재 구조에 맞게 확장할 수 있다.


### 6.4 필수 기본 컬럼

Importer가 최소한 요구하는 기본 컬럼은 다음과 같다.

    entry_year
    grade
    semester
    course_name
    course_code
    completion_type
    credits
    notes

변경 이력용 컬럼은 기존 파일과의 호환성을 위해 선택적으로 읽을 수 있지만, 현재 유지보수 대상 seed는 가능하면 19개 컬럼 전체를 갖추는 것을 권장한다.


### 6.5 CSV 인코딩

현재 importer는 CSV를 다음 인코딩으로 읽는다.

    utf-8-sig

따라서 UTF-8 BOM이 있는 파일도 정상적으로 처리할 수 있다.

기존 파일에 BOM이 있다면 단순 수정 과정에서 불필요하게 제거하거나 다시 추가하지 않는 것이 좋다.

인코딩이나 줄바꿈 형식이 바뀌면 실제 내용은 거의 변하지 않았는데 Git diff에서 파일 전체가 수정된 것처럼 보일 수 있다.


### 6.6 불필요한 전체 파일 재작성 방지

Seed를 자동 스크립트로 수정할 때 가장 주의해야 할 점 중 하나는 CSV 전체 재직렬화이다.

Python의 `csv.DictWriter` 등으로 파일 전체를 다시 쓰면 다음이 달라질 수 있다.

- 줄바꿈 형식
- BOM
- 따옴표 사용 방식
- 빈 필드 표현
- 행 전체의 formatting

이 경우 실제로는 10개 행만 수정했어도 Git에서 100개 행 전체가 변경된 것처럼 보일 수 있다.

따라서 대규모 유지보수 작업에서는 가능하면 다음 원칙을 사용한다.

- 원래 행은 그대로 보존
- 실제 수정 대상 행만 변경
- 필요한 신규 행만 추가
- 헤더 확장이 필요하면 헤더만 변경
- 기존 newline 형식 보존

수정 후에는 반드시 `git diff`를 확인한다.


### 6.7 기본 값 검증

현재 importer는 다음 기본 규칙을 검증한다.

#### 학년

    1 ~ 6

범위를 벗어날 수 없다.


#### 학기

    1
    2

만 허용한다.


#### 이수구분

    전필
    전선

만 허용한다.


#### `change_role`

    current
    legacy

만 허용한다.


#### `change_type`

다음 값만 허용한다.

    1:1
    1:N
    N:1
    N:M


### 6.8 일반 current 과목

구조변경이 없는 일반 과목은 다음과 같이 생각한다.

    change_group = 비어 있음
    change_type = 비어 있음
    change_role = current

실제로 CSV의 `change_role`이 빈 문자열이어도 importer는 기본적으로 `current`로 읽는다.

하지만 유지보수 과정에서 변경 이력을 명확히 관리해야 하는 행에는 필요에 따라 `current`를 명시적으로 적어도 된다.


### 6.9 `change_group`이 없는 일반 과목의 제약

`change_group`이 비어 있는 일반 과목에는 구조변경 메타데이터를 넣을 수 없다.

즉 다음과 같은 조합은 잘못된 데이터이다.

    change_group = 빈 값
    change_type = 1:1

또는:

    change_group = 빈 값
    change_effective_year = 2026

또는:

    change_group = 빈 값
    change_note = ...

구조변경 메타데이터를 기록하려면 반드시 `change_group`이 있어야 한다.


### 6.10 `change_group`이 있으면 `change_type`이 필요하다

반대로:

    change_group = 2022-ANTICANCER

처럼 그룹을 지정했다면 반드시:

    change_type = 1:1

등의 구조변경 유형도 지정해야 한다.

`change_group`만 있고 `change_type`이 없는 상태는 importer가 허용하지 않는다.


### 6.11 속성변경 행 수정

동일 과목의 속성변경은 기존 현재 행을 직접 수정한다.

예를 들어:

    ADB046 임상미생물학
    2학점 → 3학점

이라면 기존 행의:

    credits

를 `3`으로 변경하고:

    previous_credits = 2
    attribute_change_effective_year = 2025
    attribute_change_note = ...

를 기록한다.

별도의 legacy 행을 추가하지 않는다.


### 6.12 변경되지 않은 `previous_*` 값은 비워 둔다

예를 들어 학점만 변경되었다면:

    previous_credits = 2

만 기록한다.

다음 값은 비워 둔다.

    previous_completion_type
    previous_grade
    previous_semester

`previous_*`는 과거 행 전체를 복사하는 필드가 아니다.

실제로 변경된 속성만 기록한다.


### 6.13 속성변경 metadata의 제약

다음 필드는 속성변경에 대한 metadata이다.

    attribute_change_effective_year
    attribute_change_note

이 metadata만 존재하고 실제 `previous_*` 값이 하나도 없다면 잘못된 데이터이다.

예를 들어 다음은 허용하지 않는다.

    previous_credits =
    previous_completion_type =
    previous_grade =
    previous_semester =
    attribute_change_effective_year = 2026

실제 이전 속성이 최소 하나는 있어야 한다.


### 6.14 속성변경 적용 연도 범위

현재 importer는:

    attribute_change_effective_year

와:

    change_effective_year

을 일반적인 연도 범위 안의 정수로 검사한다.

유지보수에서는 실제 cohort 적용 연도를 정확히 기록해야 한다.

예:

    2024
    2025
    2026

문자열 설명이나 학기까지 넣지 않는다.

잘못된 예:

    2026-1
    2026학년도
    Spring 2026

학기는 현재 `grade` / `semester` 또는 note에서 설명한다.


### 6.15 1:1 구조변경 수정

기존 과목이 새 과목으로 대체된 경우 기존 행은 삭제하지 않고 `legacy`로 전환한다.

예:

    ADB075 지역약국 예비실무실습

기존 행:

    change_group = 2022-COMMUNITY-PRE-PRACTICE
    change_type = 1:1
    change_role = legacy
    change_effective_year = 2026

그리고 새 current 행을 추가한다.

    ADA115 지역약국 예비실무실습

    change_group = 2022-COMMUNITY-PRE-PRACTICE
    change_type = 1:1
    change_role = current
    change_effective_year = 2026

두 행은 동일한 `change_group`과 `change_type`을 공유해야 한다.


### 6.16 구조변경에서 기존 행을 삭제하지 않는다

구조변경을 표현하기 위해 과거 과목을 seed에서 완전히 삭제하면 안 된다.

예:

    ADB075 삭제
    ADA115만 추가

이렇게 하면 현재 과목은 표현할 수 있지만 다음 정보를 잃는다.

- 과거 학정번호
- 과거 과목 위치
- 과거 학점
- 과거 이수구분
- 어떤 과목에서 변경되었는지

따라서 구조변경에서는 기존 행을 `legacy`로 보존한다.


### 6.17 1:N 구조변경 수정

예:

    ADB068 독성학
        ↓
    ADA234 독성학1
    ADA235 독성학2

기존 ADB068:

    change_role = legacy

새 ADA234:

    change_role = current

새 ADA235:

    change_role = current

세 행 모두:

    change_group = 동일 값
    change_type = 1:N

을 사용한다.


### 6.18 N:1 구조변경 수정

예:

    ADB028 의약품합성학1
    ADB038 의약품합성학2
        ↓
    ADA198 의약품합성학

두 기존 행:

    change_role = legacy

새 행:

    change_role = current

세 행 모두:

    change_group = 동일 값
    change_type = N:1

을 사용한다.


### 6.19 구조변경 current 행에 `previous_*`를 중복 기록하지 않는다

예:

    ADB071 4-2
        ↓
    ADA145 5-1

이라면:

    ADB071
        legacy
        grade = 4
        semester = 2

    ADA145
        current
        grade = 5
        semester = 1

로 저장한다.

ADA145에 다시:

    previous_grade = 4
    previous_semester = 2

를 넣지 않는다.

구조변경 이전 상태는 legacy 행 자체가 이미 보존하고 있다.


### 6.20 신규 과목 추가

실제 개설에서 새롭게 확인되었고 기존 과목과 구조적 관계가 없다면 새 current 행을 추가한다.

예:

    2022,5,2,약사와 건강증진,ADA239,전선,2,...

이 경우 일반적으로 다음은 비워 둔다.

    change_group
    change_type
    change_effective_year
    change_note
    previous_credits
    previous_completion_type
    previous_grade
    previous_semester
    attribute_change_effective_year
    attribute_change_note

그리고 `notes`에 추가 근거를 기록한다.


### 6.21 `notes` 작성

`notes`는 해당 행이 왜 그 값을 가지는지 나중에 다시 확인할 수 있도록 작성한다.

좋은 예:

    2022학번이 5학년이던 2026학년도 2학기
    실제 개설 이력에 따라 추가된 전공선택 과목.

또는:

    2022학년도 공식 교육과정표 기준.

나쁜 예:

    수정함.
    최신값.
    확인됨.

나중에 다른 사람이 보아도 어떤 자료와 시점을 기준으로 했는지 이해할 수 있어야 한다.


### 6.22 `change_note` 작성

구조변경 note에는 최소한 다음 정보가 드러나도록 한다.

- 대상 cohort
- 기존 과목
- 새 과목 또는 구조
- 적용 시점

예:

    2022학번 기준 의료기관약국 예비실습이
    5학년 2학기 ADB086에서
    5학년 1학기 ADA217 의료기관약국 예비실무실습으로 변경됨.


### 6.23 `attribute_change_note` 작성

속성변경 note에는 무엇이 어떻게 변경되었는지 직접 적는다.

예:

    2022학번 기준 임상미생물학이
    2025학년도 4학년 1학기 개설에서
    2학점에서 3학점으로 변경됨.

또는:

    2022학번 기준 건강기능식품학이
    4학년 1학기에서
    2025학년도 4학년 2학기로 이동함.


### 6.24 숫자 필드 작성

다음은 정수로 기록한다.

    entry_year
    grade
    semester
    change_effective_year
    previous_grade
    previous_semester
    attribute_change_effective_year

학점은 importer에서 숫자로 파싱한다.

예:

    2
    2.0
    3

모두 숫자로 읽을 수 있다.

다만 seed 파일 내에서는 기존 형식과 일관성을 유지하는 것이 좋다.


### 6.25 과목 코드가 없는 경우

`course_code`는 optional로 읽을 수 있다.

실제 공식 교육과정에 학정번호가 없거나 아직 정확한 코드를 확인하지 못한 특수한 경우에는 빈 값이 존재할 수 있다.

하지만 실제 개설 이력과 매핑되는 현재 과목이라면 가능한 한 대표 학정번호를 확보한다.

학정번호 누락은 audit과 사용자 수강기록 매칭의 정확도를 떨어뜨린다.


### 6.26 중복 행 방지

Importer는 다음 값을 조합해 중복 교육과정 행을 검사한다.

    grade
    semester
    course_name
    course_code
    change_role

동일한 조합이 두 번 존재하면 오류가 발생할 수 있다.

신규 current 행을 추가하기 전에 기존 seed에 동일한 행이 이미 존재하는지 반드시 확인한다.


### 6.27 구조변경 그룹 내 일관성

같은 `change_group`의 행들은 하나의 변경 사건을 나타낸다.

따라서 다음 값이 서로 모순되지 않도록 한다.

    change_group
    change_type
    change_effective_year
    change_note

예를 들어 같은 그룹 안에서:

    legacy → change_type = 1:1
    current → change_type = 1:N

처럼 서로 다른 유형을 사용하면 안 된다.


### 6.28 행 순서

현재 기능적으로 가장 중요한 것은 데이터 값 자체이며, CSV의 행 순서는 과목 식별의 핵심 키가 아니다.

그러나 사람이 읽기 쉽게 유지하는 것이 좋다.

일반적으로:

- 기존 교육과정 행의 순서는 가급적 유지
- 기존 행을 불필요하게 재정렬하지 않음
- 구조변경으로 추가된 current 행은 기존 파일의 변경 이력 구역 또는 일관된 위치에 배치
- 신규 과목도 일관된 방식으로 추가

를 권장한다.

대규모 자동 정렬은 Git diff를 불필요하게 키울 수 있으므로 피한다.


### 6.29 수정 스크립트를 사용할 때

변경량이 많으면 Python 스크립트나 일회성 heredoc으로 seed를 수정할 수 있다.

이 경우 다음 원칙을 지킨다.

1. 대상 학번을 명시적으로 제한
2. 예상 기존 행 수 검증
3. 수정할 course code가 정확히 하나인지 검증
4. 추가될 행 수 검증
5. current / legacy 예상 수 검증
6. 수정 후 핵심 과목 값을 assertion으로 확인
7. 파일을 쓰기 전에 가능한 한 실패 조건을 먼저 검사

예를 들어:

    assert initial_count == 101
    assert final_count == 121
    assert legacy_count == 16
    assert attribute_count == 11

같은 검증을 넣을 수 있다.

단, 이 숫자는 특정 학번 작업의 예시이며 다른 cohort에 그대로 사용하지 않는다.


### 6.30 일회성 heredoc 수정의 주의점

터미널에서:

    python - <<'PY'
    ...
    PY

형태로 실행한 스크립트는 실행이 끝나면 수정할 수 있는 파일로 남지 않는다.

따라서 실행 후 문제가 발견되었다면 "위 스크립트의 일부만 수정해서 다시 실행"하는 방식으로 안내하면 안 된다.

반드시 완전한 수정 명령을 다시 작성하거나, 별도의 스크립트 파일로 저장해서 작업한다.


### 6.31 수정 직후 Git diff 확인

Seed 수정이 끝나면 가장 먼저 다음을 확인한다.

    git diff --stat -- data/seed/curriculum_2022.csv

그리고:

    git diff -- data/seed/curriculum_2022.csv

을 확인한다.

`--stat`에서는 변경량이 의도한 수준인지 본다.

예를 들어 20여 개 행을 수정했는데:

    1 file changed, 500 insertions(+), 500 deletions(-)

처럼 파일 전체가 바뀌었다면 newline이나 encoding 문제를 의심한다.


### 6.32 Diff에서 확인할 항목

실제 diff를 보면서 다음을 점검한다.

- 헤더가 예상대로 유지 또는 확장되었는가
- 수정하려던 과목만 변경되었는가
- 변경 전 값이 올바르게 `previous_*`에 들어갔는가
- 구조변경 legacy 행이 삭제되지 않았는가
- 새 current 행이 정확히 추가되었는가
- 신규 과목이 중복 추가되지 않았는가
- 잘못된 학점이나 이수구분이 없는가
- notes가 의도와 맞는가
- BOM 또는 줄바꿈 때문에 전체 파일이 변경되지 않았는가


### 6.33 수정 후 Audit을 먼저 실행한다

Git diff가 정상이어도 바로 SQLite import를 하지 않는다.

먼저:

    python scripts/audit_curriculum.py \
      --entry-year 2022

를 다시 실행한다.

목표는 수정 전 발견되었던 후보들이 실제로 해소되었는지 확인하는 것이다.


### 6.34 Audit 결과가 악화되면 수정 중단

Seed를 수정한 뒤 다음과 같은 현상이 생기면 DB 반영으로 넘어가지 않는다.

- 새로운 `CREDIT_MISMATCH` 발생
- 새로운 `UNMAPPED_OFFERING` 발생
- 예상하지 못한 code-change candidate 발생
- 기존 exact match가 candidate로 바뀜
- 신규 과목이 중복 대응됨
- 구조변경 current와 legacy가 잘못 매핑됨

원인을 먼저 확인하고 seed를 다시 수정한다.


### 6.35 Seed 수정 완료 기준

Seed 수정 단계는 다음 조건을 만족하면 완료된 것으로 본다.

- 필요한 실제 변경이 모두 기록됨
- 단순 오류와 실제 변경 이력이 구분됨
- `previous_*`가 동일 과목 속성변경에만 사용됨
- `change_*`가 구조변경에만 사용됨
- legacy 과거 행이 보존됨
- 신규 과목이 current로 추가됨
- cohort 적용 시점이 올바름
- Git diff가 의도한 범위임
- Audit 재실행 결과가 설명 가능함

이 상태가 된 뒤에야 SQLite import 단계로 넘어간다.


### 6.36 핵심 원칙

Seed CSV 수정에서 가장 중요한 것은 단순히 "현재 값이 맞는 파일"을 만드는 것이 아니다.

목표는 다음 세 가지를 동시에 만족하는 것이다.

    현재 교육과정이 정확하다
    +
    실제 변경 이력이 보존된다
    +
    Git과 DB에서 안전하게 추적할 수 있다

따라서 수정 과정에서는 현재 값뿐 아니라 **왜 그 값이 되었는지와 이전 상태를 어떤 방식으로 보존할 것인지**까지 함께 판단해야 한다.


## 7. SQLite 반영 및 검증

### 7.1 SQLite 반영의 목적

Seed CSV 수정과 audit 검증이 끝나면 해당 교육과정을 로컬 SQLite DB에 반영한다.

현재 사용하는 importer는 다음과 같다.

    scripts/import_curriculum.py

대상 DB는 다음 파일이다.

    data/db/inyak.db

이 단계의 목적은 수정한 seed가 실제 `curriculum_courses` 테이블에 정상적으로 들어가는지 확인하고, 웹과 백엔드가 사용하는 로컬 데이터 구조에서도 문제가 없는지 검증하는 것이다.


### 7.2 Import 실행 전 조건

SQLite import로 넘어가기 전에 다음 조건을 만족해야 한다.

- 대상 `curriculum_YYYY.csv` 수정 완료
- Git diff에서 의도하지 않은 대규모 변경 없음
- `scripts/audit_curriculum.py` 재실행 완료
- 설명되지 않는 학점 mismatch 없음
- 설명되지 않는 역방향 candidate 없음
- 신규 과목과 구조변경 분류 완료
- current / legacy 예상 구조를 미리 알고 있음

Audit이 아직 정리되지 않은 상태에서 DB부터 수정하지 않는다.


### 7.3 Import 명령

프로젝트 루트에서 실행한다.

예: 2022학번

    cd /Users/younyung.gene/inyak-planner

    python scripts/import_curriculum.py \
      data/seed/curriculum_2022.csv

2023학번이라면:

    python scripts/import_curriculum.py \
      data/seed/curriculum_2023.csv

와 같이 대상 seed만 변경한다.


### 7.4 SQLite importer의 동작 방식

SQLite importer는 해당 CSV에 포함된 `entry_year` 하나를 읽고 그 학번의 `curriculum_courses` 데이터를 교체한다.

현재 방식은 다음과 같다.

    DELETE FROM curriculum_courses
    WHERE entry_year = 대상 학번

그 뒤 CSV의 전체 행을 다시 INSERT한다.

즉 SQLite에서는 해당 학번 데이터가 **전체 교체**된다.

다른 학번의 `curriculum_courses` 데이터에는 영향을 주지 않는다.

또한 실제 수강편람 데이터인:

    courses

테이블에는 영향을 주지 않는다.


### 7.5 PostgreSQL 방식과 혼동하지 않는다

SQLite importer와 PostgreSQL importer의 동작 방식은 다르다.

SQLite:

    해당 entry_year 전체 DELETE
        ↓
    CSV 전체 INSERT

PostgreSQL:

    기존 ID를 최대한 보존하면서
    UPDATE / INSERT / 필요한 경우 DELETE

따라서 SQLite에서 사용하는 import 방식을 PostgreSQL에 그대로 적용하면 안 된다.

PostgreSQL의 `curriculum_courses.id`는 사용자 수강기록에서 참조될 수 있기 때문이다.

SQLite는 로컬 기준 DB이므로 해당 cohort를 단순 재구성할 수 있지만, 운영 PostgreSQL은 ID 보존이 중요하다.


### 7.6 Importer가 먼저 검증하는 항목

Importer는 DB에 쓰기 전에 CSV 구조를 검증한다.

대표적으로 다음을 확인한다.

- CSV 헤더 존재 여부
- 필수 컬럼 존재 여부
- 하나의 CSV에 하나의 `entry_year`만 존재하는지
- 학년이 1~6인지
- 학기가 1 또는 2인지
- 이수구분이 `전필` 또는 `전선`인지
- `change_role`이 `current` 또는 `legacy`인지
- `change_type`이 허용된 값인지
- 중복 교육과정 행이 있는지
- 구조변경 그룹의 형태가 올바른지
- 변경 적용 연도가 정상 범위인지
- attribute metadata와 `previous_*`의 관계가 올바른지

문제가 있으면 import를 중단한다.


### 7.7 구조변경 그룹 검증

Importer는 같은 `change_group`에 속하는 행들이 같은 `change_type`을 사용하는지 검사한다.

또한 각 유형별 legacy/current 개수도 확인한다.

#### `1:1`

    legacy = 1
    current = 1


#### `1:N`

    legacy = 1
    current >= 2


#### `N:1`

    legacy >= 2
    current = 1


#### `N:M`

    legacy >= 2
    current >= 2

예를 들어:

    change_type = 1:N
    legacy = 1
    current = 1

이라면 구조가 잘못된 것으로 판단하고 import를 중단한다.


### 7.8 구조변경 적용 연도 일관성

같은 `change_group`에 속한 모든 행은 동일한 `change_effective_year`을 가져야 한다.

예:

    2022-TOXICOLOGY

    ADB068 legacy → 2026
    ADA234 current → 2026
    ADA235 current → 2026

정상이다.

반대로 같은 그룹에서:

    legacy → 2025
    current → 2026

처럼 서로 다르면 importer가 오류로 처리한다.


### 7.9 Import 완료 출력

정상적으로 끝나면 다음과 같은 요약이 나온다.

예:

    2022학번 교육과정 import 완료
    전체 행: 121개
    현재 과목: 105개
    변경 전 과목: 16개
    현재 전필 학점: 122
    현재 전선 개설학점: 117
    현재 과목 중 대표 학정번호 미지정: 0개

각 값은 반드시 확인한다.


### 7.10 `전체 행`

해당 학번의 `curriculum_courses`에 저장된 전체 행 수이다.

다음을 모두 포함한다.

    current
    +
    legacy

따라서 구조변경 이력이 많아질수록 공식 현재 과목 수보다 전체 행 수가 더 커질 수 있다.


### 7.11 `현재 과목`

다음 조건의 행 개수이다.

    change_role = 'current'

현재 교육과정 화면 및 학점 합계를 구성하는 기준이 된다.

일반 과목도 `change_role`이 비어 있는 CSV에서는 importer가 기본적으로 `current`로 해석한다.


### 7.12 `변경 전 과목`

다음 조건의 행 개수이다.

    change_role = 'legacy'

구조변경 전 상태를 보존하는 행이다.

현재 전필·전선 학점 합계에는 포함되지 않는다.


### 7.13 `현재 전필 학점`

다음 행들의 학점 합계이다.

    change_role = current
    completion_type = 전필

Legacy 과목은 제외한다.

이 값은 **현재 seed에 존재하는 전필 과목의 총 학점**이다.

졸업요건 테이블에 저장된 공식 최소 전필 학점과 반드시 같아야 하는 값은 아니다.

교육과정 개편으로 실제 current 전필 개설학점이 공식 최소 졸업학점보다 많을 수도 있으므로 두 개념을 구분한다.


### 7.14 `현재 전선 개설학점`

다음 행들의 학점 합계이다.

    change_role = current
    completion_type = 전선

이 값 역시 현재 seed에 존재하는 전선 과목의 **개설학점 총합**이다.

학생이 졸업을 위해 반드시 모두 이수해야 하는 학점이라는 뜻이 아니다.

예를 들어:

    현재 전선 개설학점 = 117

이라고 해서 졸업에 전선 117학점이 필요한 것은 아니다.

실제 최소 졸업 전선 학점은 별도의 졸업요건 데이터에서 관리한다.


### 7.15 `대표 학정번호 미지정`

다음 조건의 current 과목 수를 보여준다.

    change_role = current
    course_code IS NULL

가능하면 이 값은 0이 되는 것이 좋다.

학정번호가 없는 current 과목은 다음 기능의 정확도를 떨어뜨릴 수 있다.

- 실제 수강이력 매칭
- audit
- 교육과정 과목 식별
- 사용자 이수현황 연결

단, 공식 자료 자체에 코드가 없거나 아직 대표 코드를 확정하지 못한 특수한 경우에는 0이 아닐 수 있다.


### 7.16 Import 직후 기본 SQL 검증

Importer 출력만 보고 끝내지 않고 SQLite에서 직접 확인하는 것을 권장한다.

예: 2022학번

    sqlite3 data/db/inyak.db

접속 후:

    SELECT
        COUNT(*) AS total_rows,
        SUM(
            CASE
                WHEN change_role = 'current'
                THEN 1
                ELSE 0
            END
        ) AS current_rows,
        SUM(
            CASE
                WHEN change_role = 'legacy'
                THEN 1
                ELSE 0
            END
        ) AS legacy_rows
    FROM curriculum_courses
    WHERE entry_year = 2022;

예상한 전체/current/legacy 수와 일치하는지 확인한다.


### 7.17 Attribute Change 개수 확인

속성변경이 예상대로 저장되었는지 확인한다.

    SELECT COUNT(*) AS attribute_change_count
    FROM curriculum_courses
    WHERE entry_year = 2022
      AND change_role = 'current'
      AND (
          previous_credits IS NOT NULL
          OR previous_completion_type IS NOT NULL
          OR previous_grade IS NOT NULL
          OR previous_semester IS NOT NULL
      );

예를 들어 수정 과정에서 11개의 속성변경을 만들었다면 결과도:

    11

이어야 한다.


### 7.18 Attribute Change 상세 확인

개수뿐 아니라 실제 값도 확인하는 것이 좋다.

    SELECT
        course_code,
        course_name,
        grade,
        semester,
        completion_type,
        credits,
        previous_grade,
        previous_semester,
        previous_completion_type,
        previous_credits,
        attribute_change_effective_year
    FROM curriculum_courses
    WHERE entry_year = 2022
      AND change_role = 'current'
      AND (
          previous_credits IS NOT NULL
          OR previous_completion_type IS NOT NULL
          OR previous_grade IS NOT NULL
          OR previous_semester IS NOT NULL
      )
    ORDER BY
        attribute_change_effective_year,
        course_code;

여기서 각 current 값과 previous 값이 의도대로 들어갔는지 확인한다.


### 7.19 구조변경 상세 확인

구조변경 그룹은 다음과 같이 확인한다.

    SELECT
        change_group,
        change_type,
        change_role,
        course_code,
        course_name,
        grade,
        semester,
        completion_type,
        credits,
        change_effective_year
    FROM curriculum_courses
    WHERE entry_year = 2022
      AND change_group IS NOT NULL
    ORDER BY
        change_group,
        change_role,
        course_code;

각 그룹에서 다음을 확인한다.

- legacy 행이 필요한 만큼 존재하는가
- current 행이 필요한 만큼 존재하는가
- 코드가 맞는가
- 학년/학기가 맞는가
- 학점이 맞는가
- 이수구분이 맞는가
- effective year가 같은가


### 7.20 특정 핵심 과목 직접 확인

대규모 수정에서는 모든 행을 눈으로 확인하기 어렵다.

따라서 이번 작업에서 중요한 과목들을 골라 직접 조회한다.

예:

    SELECT
        course_code,
        course_name,
        grade,
        semester,
        completion_type,
        credits,
        change_role
    FROM curriculum_courses
    WHERE entry_year = 2022
      AND course_code IN (
          'ADA198',
          'ADB111',
          'ADA115',
          'ADA148',
          'ADA217',
          'ADB103',
          'ADA237',
          'ADB113'
      )
    ORDER BY course_code;

검증 대상 코드는 실제 작업에 맞게 바꾼다.


### 7.21 현재 전필·전선 합계 직접 확인

필요하면 importer 요약과 동일한 계산을 SQL로 다시 확인할 수 있다.

    SELECT
        SUM(
            CASE
                WHEN change_role = 'current'
                 AND completion_type = '전필'
                THEN COALESCE(credits, 0)
                ELSE 0
            END
        ) AS current_required_credits,

        SUM(
            CASE
                WHEN change_role = 'current'
                 AND completion_type = '전선'
                THEN COALESCE(credits, 0)
                ELSE 0
            END
        ) AS current_elective_credits
    FROM curriculum_courses
    WHERE entry_year = 2022;


### 7.22 `current + legacy = total` 확인

기본적으로 해당 학번의 모든 행은 `current` 또는 `legacy` 중 하나로 해석되어야 한다.

따라서:

    current_rows + legacy_rows = total_rows

가 되어야 한다.

예:

    105 + 16 = 121

일치하지 않는다면 `change_role` 데이터나 import 결과를 점검한다.


### 7.23 SQLite에서 ID 보존을 검증하지 않는다

SQLite importer는 해당 학번의 행을 삭제 후 다시 삽입한다.

따라서 SQLite에서 기존 `curriculum_courses.id`가 유지되는지를 검증하는 것은 의미가 없다.

ID 보존 검증은 PostgreSQL 배포 단계에서 수행한다.

SQLite 단계에서는 다음을 검증하는 데 집중한다.

- 데이터 구조
- 값
- current / legacy 상태
- 변경 이력
- 합계
- 웹에서 사용할 수 있는 형태


### 7.24 Import 후 Audit을 다시 실행할 필요가 있는가

Audit은 seed CSV를 직접 읽기 때문에 SQLite import가 성공했다고 해서 audit 결과 자체가 바뀌지는 않는다.

따라서 정상적인 작업 순서는:

    seed 수정
        ↓
    audit
        ↓
    SQLite import

이다.

SQLite import 후 audit을 다시 실행해야 할 필수 이유는 없다.

다만 실제 `courses` 데이터까지 별도로 수정했거나 audit 과정에서 다른 파일을 건드렸다면 다시 실행해도 된다.


### 7.25 Import 실패 시 먼저 확인할 항목

`Import 실패:`가 나오면 메시지를 보고 먼저 다음을 확인한다.

#### 필수 컬럼 누락

    CSV 필수 칼럼이 없습니다

헤더를 확인한다.


#### 잘못된 학년 또는 학기

    학년 범위가 잘못됐습니다
    학기는 1 또는 2여야 합니다

대상 행을 확인한다.


#### 잘못된 이수구분

    이수구분이 잘못됐습니다

`전필` 또는 `전선`인지 확인한다.


#### 잘못된 change role/type

    change_role이 잘못됐습니다
    change_type이 잘못됐습니다

허용값을 확인한다.


#### 잘못된 구조변경 그룹

    변경 그룹 ... 구성이 올바르지 않습니다

legacy/current 개수를 확인한다.


#### 중복 행

    중복 교육과정 과목이 있습니다

같은 과목이 중복 추가되었는지 확인한다.


### 7.26 Import 실패 후 부분 반영 여부

Importer는 SQLite connection context 안에서 해당 cohort DELETE와 INSERT를 수행한다.

오류가 발생한다면 DB 상태를 임의로 추정하지 말고 직접 확인한다.

특히 스크립트를 수정하거나 DB 오류가 발생한 경우에는:

    SELECT COUNT(*)
    FROM curriculum_courses
    WHERE entry_year = 대상 학번;

으로 현재 상태를 확인한 뒤 다시 진행한다.


### 7.27 SQLite DB 직접 수정은 피한다

유지보수의 기준 데이터는 seed CSV이다.

따라서:

    sqlite3 data/db/inyak.db

에 들어가 `curriculum_courses` 값을 직접 UPDATE하여 문제를 해결하는 방식은 피한다.

그렇게 하면:

    seed CSV ≠ SQLite

상태가 되어 다음 import에서 수정 내용이 사라진다.

정상적인 수정 방향은 항상:

    seed 수정
        ↓
    audit
        ↓
    import

이다.


### 7.28 `courses` 테이블도 직접 혼동해서 수정하지 않는다

`curriculum_courses`와 `courses`는 역할이 다르다.

    curriculum_courses
        → 학번별 교육과정

    courses
        → 실제 수강편람 개설 이력

교육과정 값을 맞추기 위해 `courses`를 임의로 수정해서 audit을 통과시키면 안 된다.

`courses`가 실제 크롤링 오류 때문에 잘못된 경우에만 별도의 근거를 가지고 수정한다.


### 7.29 SQLite 단계 완료 기준

다음 조건을 모두 만족하면 SQLite 반영 단계가 완료된 것으로 본다.

- importer가 오류 없이 완료됨
- 전체 행 수가 예상과 일치
- current 행 수가 예상과 일치
- legacy 행 수가 예상과 일치
- current + legacy = total
- attribute change 개수가 예상과 일치
- 구조변경 그룹이 정상
- 주요 current 과목 값이 정상
- 현재 전필 학점이 예상과 일치
- 현재 전선 개설학점이 예상과 일치
- 대표 학정번호 미지정 수가 설명 가능함


### 7.30 실제 2022학번 완료 예시

2022학번 유지보수 후 SQLite importer 결과는 다음과 같았다.

    전체 행: 121개
    현재 과목: 105개
    변경 전 과목: 16개
    현재 전필 학점: 122
    현재 전선 개설학점: 117
    현재 과목 중 대표 학정번호 미지정: 0개

추가 SQL 검증에서는:

    total_rows = 121
    current_rows = 105
    legacy_rows = 16
    attribute_change_count = 11

을 확인하였다.

이와 같이 각 작업에서는 **수정 전에 예상한 구조와 import 후 실제 구조를 비교**해야 한다.


### 7.31 다음 단계

SQLite 반영과 검증이 완료되면 바로 운영 DB로 넘어가지 않는다.

다음 순서는:

    Git diff 최종 확인
        ↓
    관련 seed 파일 commit
        ↓
    dev 브랜치 push
        ↓
    최신 GitHub dev 재확인
        ↓
    개발 PostgreSQL dry-run

이다.

PostgreSQL에서는 사용자 데이터와 연결된 기존 ID 보존이 중요하므로 SQLite와 다른 배포 절차를 사용한다.


### 7.32 핵심 원칙

SQLite 단계의 핵심은 다음과 같다.

> Seed가 기준 데이터이고 SQLite는 그 seed를 실제 애플리케이션용 로컬 테이블에 재현한 결과이다.

따라서 SQLite에서 값을 직접 고치는 것이 아니라, **seed가 정확한지 확인하고 importer가 그것을 정확히 재현하는지 검증하는 단계**로 사용한다.


## 8. Git 반영

### 8.1 Git 반영의 목적

SQLite 검증까지 완료되면 수정한 seed 파일을 Git에 반영한다.

이 단계의 목적은 단순히 변경사항을 저장하는 것이 아니다.

교육과정 데이터는 이후 개발 DB와 운영 DB에 반영되므로, **어떤 seed가 DB 반영의 기준이 되었는지 Git history에서 추적 가능하도록 만드는 것**이 중요하다.

따라서 PostgreSQL 반영 전에 먼저 관련 seed 변경을 `dev` 브랜치에 commit / push하는 것을 기본 순서로 한다.


### 8.2 Git 반영 전 최종 확인

커밋 전에 다음 세 가지를 다시 확인한다.

    git status

    git diff --stat

    git diff -- data/seed/curriculum_YYYY.csv

특히 교육과정 작업에서는 실제 수정 대상과 무관한 파일이 함께 변경되어 있지 않은지 확인한다.


### 8.3 `git status` 확인

프로젝트 루트에서:

    cd /Users/younyung.gene/inyak-planner

    git status

를 실행한다.

확인할 항목:

- 현재 브랜치가 `dev`인가
- 수정한 seed 파일이 보이는가
- 예상하지 못한 다른 파일 수정이 있는가
- untracked 파일이 있는가
- 이미 staged된 다른 작업이 있는가

교육과정 작업과 무관한 변경이 있으면 무조건 함께 커밋하지 않는다.


### 8.4 현재 브랜치 확인

필요하면:

    git branch --show-current

로 현재 브랜치를 확인한다.

교육과정 유지보수 작업의 기본 대상은:

    dev

브랜치이다.

실수로 `main`에서 직접 작업하고 있다면 바로 push하지 말고 현재 변경 상태를 먼저 확인한다.


### 8.5 Diff 통계 확인

예:

    git diff --stat -- data/seed/curriculum_2022.csv

출력 예:

    data/seed/curriculum_2022.csv | 72 +++++++++++++++++++++++++++----------------
    1 file changed, 46 insertions(+), 26 deletions(-)

이 단계에서는 변경량이 실제 작업 규모와 대략 일치하는지 본다.


### 8.6 비정상적으로 큰 Diff

실제로는 소수 행만 수정했는데 다음과 같이 나온다면:

    1 file changed, 500 insertions(+), 500 deletions(-)

내용 수정 전에 encoding 또는 newline 변경을 의심한다.

대표적인 원인:

- CRLF ↔ LF 변경
- UTF-8 BOM 제거 또는 추가
- CSV 전체 재직렬화
- 따옴표 처리 방식 변경
- 자동 포맷팅

이 경우 그대로 커밋하지 말고 원인을 먼저 확인한다.


### 8.7 실제 Diff 확인

다음 명령으로 변경 내용을 직접 확인한다.

    git diff -- data/seed/curriculum_2022.csv

확인할 내용:

- 변경하려던 과목만 수정되었는가
- 기존 값이 `previous_*`에 정확히 들어갔는가
- legacy 행이 유지되었는가
- 새 current 행이 추가되었는가
- 신규 과목이 올바르게 추가되었는가
- 헤더가 정상인가
- notes와 change note가 맞는가
- 의도하지 않은 값 변경이 없는가


### 8.8 SQLite DB 파일은 일반적으로 커밋 대상과 구분한다

교육과정 유지보수의 기준 데이터는 seed CSV이다.

로컬 SQLite DB는 seed와 crawler 데이터를 이용한 실행·검증용 데이터이므로, 해당 저장소의 현재 관리 정책에 따라 커밋 여부를 판단한다.

교육과정 seed 작업을 커밋할 때는 무조건:

    data/db/inyak.db

까지 같이 stage한다고 생각하지 않는다.

항상 `git status`와 `.gitignore` 정책을 먼저 확인한다.


### 8.9 관련 파일만 Stage

2022학번 seed만 수정했다면:

    git add data/seed/curriculum_2022.csv

와 같이 대상 파일을 명시적으로 stage하는 것이 안전하다.

다음처럼 모든 변경을 한 번에 stage하는 방식은 피하는 것이 좋다.

    git add .

특히 프로젝트에서 동시에 다른 기능 개발이 진행 중이라면 unrelated 변경이 섞일 수 있다.


### 8.10 Stage 결과 확인

Stage한 뒤 다시:

    git status

를 확인한다.

그리고 필요하면:

    git diff --cached

를 확인한다.

이 단계에서 실제 커밋에 들어갈 내용이 의도한 범위와 일치해야 한다.


### 8.11 Commit 메시지

Commit 메시지는 어떤 학번의 어떤 종류 작업인지 알 수 있도록 작성한다.

예:

    git commit -m "Update 2022 curriculum changes"

또는:

    git commit -m "Audit and update 2023 curriculum"

너무 모호한 메시지는 피한다.

좋지 않은 예:

    update
    fix csv
    changes

나중에 교육과정 변경 원인을 Git history에서 추적할 수 있어야 한다.


### 8.12 Commit 후 상태 확인

Commit 후:

    git status

를 실행한다.

교육과정 작업과 관련된 변경이 모두 commit되었는지 확인한다.

다른 작업 파일이 남아 있는 것은 괜찮지만, 방금 교육과정 작업에서 필요한 파일이 빠진 것은 아닌지 확인한다.


### 8.13 Dev 브랜치 Push

Commit이 정상이라면:

    git push origin dev

로 원격 `dev`에 반영한다.

Push가 성공했다고 해서 바로 개발 DB를 수정하지 않는다.

다음 단계에서 **GitHub의 최신 dev를 다시 확인**한다.


### 8.14 왜 Push 후 GitHub를 다시 확인하는가

로컬에서 방금 push했더라도 이후 DB 반영의 기준은 원격 `dev` 상태로 다시 확인하는 것을 원칙으로 한다.

이유는 다음과 같다.

- 실제 push가 원하는 commit을 포함했는지 확인
- 다른 변경이 원격에 추가되었는지 확인
- seed와 importer가 최신 상태인지 확인
- 작업 중 로컬과 원격이 달라졌는지 확인
- 다음 작업 세션에서도 동일한 기준을 사용하기 위함

즉:

    local에서 잘 보임

만으로 PostgreSQL 반영을 결정하지 않는다.


### 8.15 GitHub는 DB 반영 전 기준점이다

PostgreSQL 반영 전에 최소한 다음을 최신 `dev`에서 확인한다.

- 대상 `curriculum_YYYY.csv`
- `scripts/import_curriculum_postgres.py`
- 필요한 경우 `scripts/import_curriculum.py`
- 필요한 경우 audit 관련 스크립트

특히 importer가 최근 수정된 경우 예전에 사용하던 명령이나 동작 방식을 기억에 의존해서 사용하지 않는다.


### 8.16 로컬 출력과 GitHub가 다를 때

GitHub의 최신 `dev`와 사용자의 현재 로컬 파일이 다르면 이유를 먼저 확인한다.

가능한 경우:

- commit하지 않은 로컬 변경
- push하지 않은 commit
- 다른 세션에서 수정된 원격 dev
- 잘못된 branch에서 작업
- merge 후 로컬 미갱신

DB 반영 전에 어떤 seed가 기준인지 명확히 해야 한다.


### 8.17 사용자가 제공한 로컬 결과의 우선순위

GitHub를 기준으로 repo 상태를 확인하더라도, 사용자가 방금 실행한 로컬:

- `git diff`
- audit 결과
- importer 출력
- SQL 결과
- build error

등은 현재 로컬 진단에서 매우 중요한 근거이다.

즉:

    GitHub
        → 최신 저장소 기준 확인

    사용자 로컬 출력
        → 실제 현재 작업 상태 확인

두 가지를 함께 사용한다.

특히 사용자가 붙여넣은 실제 오류 로그를 무시하고 GitHub 코드만 보고 상황을 추정하지 않는다.


### 8.18 Seed와 DB의 관계

PostgreSQL DB는 Git repository의 commit에 자동으로 따라가는 것이 아니다.

즉:

    git push origin dev

를 했다고 해서 Supabase의 `curriculum_courses`가 자동으로 업데이트되는 것은 아니다.

반드시 별도의 PostgreSQL import 단계가 필요하다.

전체 관계는 다음과 같다.

    seed CSV 수정
        ↓
    Git dev 반영
        ↓
    PostgreSQL importer 실행
        ↓
    개발 DB 반영

Git과 DB는 별도의 시스템이므로 둘 모두 검증해야 한다.


### 8.19 Commit 전에 PostgreSQL을 먼저 수정하지 않는 이유

기술적으로는 로컬 seed를 사용해 먼저 DB를 수정할 수도 있다.

하지만 유지보수 절차에서는 가능하면:

    seed 확정
        ↓
    Git commit / push
        ↓
    DB 반영

순서를 따른다.

이렇게 해야 나중에 DB에 들어간 데이터가 어떤 source file 기준인지 추적하기 쉽다.

DB에는 변경되었는데 Git에는 그 seed가 없는 상태를 만들지 않는 것이 좋다.


### 8.20 Git History의 역할

교육과정 변경 여부를 조사할 때 Git history도 참고 자료가 될 수 있다.

예를 들어 특정 학점이:

    2 → 3

으로 바뀐 기록이 Git에 있다면 다음을 조사할 수 있다.

- 처음 seed 작성 때부터 3이어야 했는데 잘못 입력된 것인가
- 실제 교육과정 변경을 반영하면서 수정한 것인가
- 단순 정정 commit인가

다만 Git history 자체가 공식 교육과정 근거는 아니다.

Git은 **우리 데이터가 어떻게 수정되었는지 보여주는 기록**이고, 실제 교육과정 변경 여부는 공식 자료와 수강편람으로 판단한다.


### 8.21 Git History가 없는 경우

오래된 seed는 초기 import 한 번만 존재하고 이후 변경 과정이 Git에 남아 있지 않을 수 있다.

이 경우 Git에서 과거 상태를 억지로 복원하려고 하지 않는다.

다음 자료를 사용한다.

- 공식 교육과정표
- 실제 연도별 수강편람
- audit
- cohort mapping
- 다른 학번 seed
- 기존 notes

Git history는 보조 근거이지 필수 근거가 아니다.


### 8.22 여러 학번을 동시에 수정하는 경우

가능하면 한 학번씩:

    audit
    수정
    검증
    commit

하는 것이 좋다.

여러 학번을 한 commit에 묶으면 다음이 어려워질 수 있다.

- 특정 cohort 변경 추적
- rollback
- diff 검토
- DB 반영 범위 확인

다만 동일한 구조 변경을 여러 학번에 동시에 정리하는 등 명확한 이유가 있다면 함께 commit할 수 있다.

그 경우 commit 메시지와 diff에서 범위를 명확히 확인한다.


### 8.23 Script 수정이 함께 필요한 경우

교육과정 유지보수 중 importer나 audit의 버그를 발견해 스크립트도 수정해야 할 수 있다.

이 경우:

    seed 변경
    +
    script 변경

이 같은 commit에 들어갈 수 있지만, 각각 왜 필요한지 명확해야 한다.

특히 script 동작 자체가 바뀌었다면 기존 cohort에 부작용이 없는지 별도로 검증한다.


### 8.24 Frontend 변경이 없는 경우 Build는 필요하지 않다

교육과정 seed, Python script, SQLite/PostgreSQL 데이터만 수정한 경우:

    npm run build

를 의무적으로 실행할 필요는 없다.

Frontend 파일을 수정한 경우에만 frontend build 검증을 수행한다.

교육과정 데이터 반영만으로 끝나는 작업에서 불필요하게 frontend build 단계를 추가하지 않는다.


### 8.25 Frontend도 수정했다면

교육과정 변경내역 렌더링 방식 등 frontend 코드를 함께 수정했다면 frontend 작업이 끝난 뒤:

    cd /Users/younyung.gene/inyak-planner/web

    npm run build

를 실행한다.

Build 성공을 확인한 뒤 해당 frontend 변경도 commit한다.


### 8.26 Push 실패 시

`git push origin dev`가 실패하면 메시지를 먼저 읽는다.

대표적으로:

- remote에 새 commit 존재
- 인증 문제
- branch mismatch
- non-fast-forward

등이 있을 수 있다.

이 경우 무조건 force push하지 않는다.

특히:

    git push --force

는 교육과정 유지보수의 일반 절차에서 사용하지 않는다.

원격 변경을 먼저 확인하고 안전하게 병합 또는 최신화한다.


### 8.27 `main`에는 바로 Push하지 않는다

교육과정 유지보수의 일반 흐름은:

    dev
        ↓
    개발 DB 검증
        ↓
    운영 DB 검증
        ↓
    필요한 경우 main 반영

이다.

따라서 seed 변경 직후 바로 `main`에 push하는 것을 기본 절차로 삼지 않는다.

운영 브랜치 반영은 전체 개발 검증이 완료된 이후 별도 단계로 진행한다.


### 8.28 Git 반영 완료 기준

다음 조건을 만족하면 Git 단계가 완료된 것으로 본다.

- 대상 seed의 최종 diff 확인
- unrelated 파일이 commit에 포함되지 않음
- 올바른 `dev` 브랜치에서 작업
- commit 성공
- push 성공
- 원격 최신 `dev`에서 대상 seed 확인
- DB 반영에 사용할 importer도 최신 dev 기준으로 재확인


### 8.29 권장 명령 흐름

예: 2022학번

    cd /Users/younyung.gene/inyak-planner

    git status

    git diff --stat -- data/seed/curriculum_2022.csv

    git diff -- data/seed/curriculum_2022.csv

    git add data/seed/curriculum_2022.csv

    git diff --cached

    git commit -m "Update 2022 curriculum changes"

    git push origin dev

실제 작업에서는 이미 확인한 명령을 필요 이상으로 반복할 필요는 없지만, 최소한 commit 전 diff와 push 후 원격 확인은 유지한다.


### 8.30 다음 단계

Git dev 반영까지 완료되면 다음 단계는:

    개발 PostgreSQL dry-run
        ↓
    UPDATE / INSERT / DELETE 계획 확인
        ↓
    --apply
        ↓
    개발 DB SQL 검증

이다.

이 단계부터는 SQLite와 달리 기존 `curriculum_courses.id` 보존이 중요해진다.


### 8.31 핵심 원칙

Git 단계의 핵심은 다음과 같다.

> PostgreSQL에 반영할 교육과정의 기준 상태를 먼저 `dev`에 확정하고, 그 원격 상태를 다시 확인한 뒤 DB 작업을 시작한다.

이렇게 해야 seed, Git history, 개발 DB, 운영 DB가 서로 다른 상태로 갈라지는 것을 방지할 수 있다.

## 9. 개발 PostgreSQL 반영 및 검증

### 9.1 개발 DB 반영의 목적

SQLite 검증과 Git `dev` 반영이 끝나면 개발용 PostgreSQL에 교육과정을 반영한다.

현재 사용하는 importer는 다음과 같다.

    scripts/import_curriculum_postgres.py

이 단계의 목적은 로컬 SQLite가 아니라 실제 개발 환경에서 사용하는 PostgreSQL의 `public.curriculum_courses`를 seed와 동기화하고, 기존 사용자 데이터와의 연결을 안전하게 유지하는 것이다.


### 9.2 개발 DB와 운영 DB를 반드시 구분한다

Inyak Planner는 개발용 Supabase와 운영용 Supabase를 별도로 사용한다.

현재 개발용 Supabase project ref:

    rkunrjwetsnonwnmatec

현재 운영용 Supabase project ref:

    alkamigyftmalimqoixa

개발 DB 작업에서는 반드시 개발 project ref를 사용한다.

    --project-ref rkunrjwetsnonwnmatec

운영 project ref를 실수로 넣지 않는다.


### 9.3 `DATABASE_URL` 확인

PostgreSQL importer는 접속 주소를 다음 환경변수에서 읽는다.

    DATABASE_URL

그리고 명령에서 전달한 `--project-ref`가 실제 `DATABASE_URL` 안에 포함되어 있는지 검사한다.

예를 들어 개발 DB 작업인데:

    --project-ref rkunrjwetsnonwnmatec

를 지정했지만 `DATABASE_URL`이 운영 DB를 가리키고 있다면 importer는 작업을 중단한다.

이 검사는 잘못된 Supabase 프로젝트에 데이터를 쓰는 것을 막기 위한 안전장치이다.


### 9.4 Project Ref 검증 실패

다음과 비슷한 오류가 나오면 작업을 진행하지 않는다.

    DATABASE_URL이 지정한 Supabase project ref와 일치하지 않습니다.

출력에는 다음 정보가 표시된다.

    요청 project ref
    접속 host

이 경우 `DATABASE_URL`이 어느 DB를 가리키는지 먼저 확인한다.

project ref 검증을 우회하거나 script를 수정해서 강제로 실행하지 않는다.


### 9.5 PostgreSQL Schema 검증

Importer는 실제 데이터를 쓰기 전에 `public.curriculum_courses`에 필요한 컬럼이 존재하는지 확인한다.

현재 필요한 주요 컬럼은 다음과 같다.

    entry_year
    grade
    semester
    course_name
    course_code
    completion_type
    credits
    notes
    change_group
    change_type
    change_role
    change_effective_year
    change_note
    previous_credits
    previous_completion_type
    previous_grade
    previous_semester
    attribute_change_effective_year
    attribute_change_note

필요한 컬럼이 하나라도 없으면 import를 중단한다.

이 경우 데이터 import보다 먼저 DB migration 또는 schema 상태를 확인한다.


### 9.6 PostgreSQL에서는 기존 ID 보존이 중요하다

SQLite importer는 해당 cohort를 삭제 후 재삽입하지만 PostgreSQL에서는 같은 방식을 사용하지 않는다.

이유는 `curriculum_courses.id`가 다른 사용자 데이터에서 참조될 수 있기 때문이다.

특히:

    public.user_course_records.curriculum_course_id

가:

    public.curriculum_courses.id

를 참조할 수 있다.

따라서 기존 교육과정 행을 전부 DELETE 후 INSERT하면 기존 사용자 수강기록의 참조가 깨질 수 있다.


### 9.7 ID 보존형 Replace

기존 cohort를 업데이트할 때는:

    --replace

옵션을 사용한다.

하지만 이 옵션은 단순한 전체 삭제 후 재삽입을 의미하지 않는다.

현재 importer는 기존 PostgreSQL 행과 새 CSV 행을 비교하여 가능한 한 기존 ID를 유지한다.

기본 흐름:

    기존 DB 행 조회
        ↓
    CSV 행과 안전하게 매칭
        ↓
    기존 과목 → UPDATE
    새 과목 → INSERT
    사라진 과목 → DELETE 후보

이 방식으로 기존 사용자 FK를 최대한 보존한다.


### 9.8 기존 행 매칭 우선순위

현재 ID 보존 매칭은 다음 우선순위를 사용한다.

    1. 동일 course_code
    2. 동일 course_name + change_role

먼저 학정번호가 같은 기존 DB 행을 찾는다.

학정번호가 변경되었더라도 과목명과 역할이 유일하게 일치하면 같은 기존 행으로 판단하여 ID를 유지할 수 있다.


### 9.9 학정번호 매칭

예를 들어 기존 DB에:

    id = 123
    ADB046 임상미생물학

이 있고 새 CSV에도:

    ADB046 임상미생물학

이 있다면 기존 `id = 123` 행을 UPDATE한다.

새로운 ID를 만들지 않는다.


### 9.10 과목명 + 역할 Fallback

학정번호가 변경된 상황에서도 기존 행을 안전하게 대응시킬 수 있는 경우가 있다.

예:

    기존:
    ADB075 지역약국 예비실무실습
    current

새 CSV에서 같은 이름과 같은 역할로 유일하게 대응할 수 있다면 importer가 기존 ID를 재사용할 수 있다.

단, 중복 또는 모호성이 있다면 자동으로 위험한 매칭을 하지 않는다.


### 9.11 CSV 내 중복 학정번호는 허용하지 않는다

ID 보존 매칭에서는 하나의 학정번호가 CSV 내 여러 과목에 중복 사용되면 안전하게 기존 행을 결정하기 어렵다.

이 경우 importer는 작업을 중단한다.

예:

    CSV에 중복 course_code가 있어 기존 ID를 안전하게 보존할 수 없습니다.

이 오류가 나오면 중복 행 또는 구조변경 설계를 먼저 확인한다.


### 9.12 기존 DB 학정번호도 유일할 때만 자동 매칭한다

기존 DB에 동일 course code가 여러 행에 존재하면 importer는 해당 코드를 단순히 하나의 기존 ID로 매칭하지 않는다.

자동 ID 보존은 유일한 대응이 가능한 경우에만 수행한다.

이 원칙은 잘못된 행의 ID를 다른 과목에 재사용하는 것을 막기 위한 것이다.


### 9.13 개발 DB Dry Run

실제 DB에 쓰기 전에 반드시 dry-run을 실행한다.

예: 2022학번

    cd /Users/younyung.gene/inyak-planner

    python scripts/import_curriculum_postgres.py \
      data/seed/curriculum_2022.csv \
      --project-ref rkunrjwetsnonwnmatec \
      --replace

`--apply`를 넣지 않으면 DB에는 아무것도 쓰지 않는다.


### 9.14 Dry Run 출력

정상적인 dry-run은 대략 다음과 같은 형태이다.

    PostgreSQL curriculum import 계획
    접속 host: postgres.rkunrjwetsnonwnmatec
    대상 학번: 2022
    전체 행: 121개
    현재 과목: 105개
    변경 전 과목: 16개
    현재 전필 학점: 122
    현재 전선 개설학점: 117
    DB 기존 2022학번 행: 101개

    기존 ID 보존 동기화 계획
      UPDATE: 101개
      INSERT: 20개
      DELETE: 0개

    DRY RUN 완료: DB에는 아무것도 쓰지 않았습니다.

이 출력 전체를 확인한 뒤 `--apply` 여부를 결정한다.


### 9.15 Dry Run에서 가장 먼저 확인할 것

다음 항목을 반드시 확인한다.

    접속 host
    대상 학번
    전체 행
    current / legacy
    전필 / 전선 개설학점
    기존 DB 행 수
    UPDATE
    INSERT
    DELETE

특히 접속 host가 개발 DB인지 먼저 확인한다.


### 9.16 UPDATE 수 해석

`UPDATE`는 기존 PostgreSQL 행의 ID를 그대로 유지하면서 새 seed 값으로 갱신되는 행 수이다.

예:

    DB 기존 행: 101
    UPDATE: 101

이라면 기존 101개의 ID가 그대로 유지될 계획이라는 의미이다.

기존 과목의:

- 학점
- 이수구분
- 학년
- 학기
- notes
- change metadata
- previous metadata

등이 UPDATE될 수 있다.


### 9.17 INSERT 수 해석

`INSERT`는 기존 DB에서 안전하게 대응되는 행이 없어서 새 ID가 필요한 행 수이다.

예를 들어 이번 수정에서:

    구조변경 current 신규 행 = 12
    완전 신규 과목 = 8

이라면:

    INSERT = 20

이 예상될 수 있다.

따라서 INSERT 수는 seed 수정 과정에서 예상한 신규 행 수와 비교한다.


### 9.18 DELETE 수 해석

`DELETE`는 기존 PostgreSQL에는 존재하지만 새 CSV와 대응되지 않아 삭제 대상이 되는 행 수이다.

교육과정 유지보수에서는 일반적으로 예상하지 않은 DELETE를 매우 주의해야 한다.

특히 구조변경 과거 행은 삭제하는 것이 아니라 `legacy`로 보존하는 것이 원칙이므로, 정상적인 업데이트에서는:

    DELETE: 0

인 경우가 많다.

단, 실제 데이터 정리로 정말 삭제해야 하는 행이 존재할 수 있으므로 DELETE가 무조건 0이어야 한다는 절대 규칙은 아니다.

중요한 것은 **각 DELETE가 왜 필요한지 설명할 수 있어야 한다는 것**이다.


### 9.19 예상하지 못한 DELETE가 나오면 중단

예상은:

    DELETE: 0

인데 dry-run에서:

    DELETE: 4

가 나온다면 `--apply`를 실행하지 않는다.

먼저 다음을 확인한다.

- CSV에서 행을 실수로 누락했는가
- legacy 행을 삭제했는가
- course code가 잘못 변경되었는가
- 이름 변경 때문에 기존 행 매칭이 끊겼는가
- 잘못된 cohort 파일을 사용했는가
- seed 행 수가 예상과 다른가


### 9.20 DELETE 대상의 사용자 참조 보호

Importer는 DELETE 후보가 있으면 실제 삭제 전에 `user_course_records`에서 해당 ID를 참조하고 있는지 확인한다.

참조 중이면 전체 작업을 중단한다.

오류 예:

    CSV에서 삭제될 교육과정 과목을 사용자 기록이 참조하고 있습니다.
    고아 curriculum_course_id 생성을 막기 위해 작업을 중단합니다.

즉 사용자 기록이 연결된 curriculum row를 무시하고 삭제하지 않는다.


### 9.21 FK 보호와 Importer 보호는 함께 사용한다

DB 자체의 foreign key가 삭제를 막을 수도 있지만 importer 역시 사전에 참조 여부를 검사한다.

따라서 안전장치는 다음 두 층으로 생각할 수 있다.

    importer의 사전 참조 검사
        +
    PostgreSQL FK 제약

이 구조 때문에 운영 중인 curriculum ID를 실수로 삭제할 가능성을 줄일 수 있다.


### 9.22 Dry Run 결과 계산

일반적으로 기존 행 수와 동기화 계획의 관계를 확인한다.

예:

    기존 행 = 101
    UPDATE = 101
    INSERT = 20
    DELETE = 0

이라면 최종 예상 행은:

    101 + 20 = 121

이다.

좀 더 일반적으로:

    최종 예상 행
    =
    기존 행
    - DELETE
    + INSERT

이다.

UPDATE는 행 수를 바꾸지 않는다.


### 9.23 Dry Run과 Seed 행 수 비교

Dry-run에 표시되는:

    전체 행

은 seed CSV 전체 행 수이다.

따라서 최종 예상 PostgreSQL 행 수와 일치해야 한다.

예:

    seed 전체 = 121

    DB 기존 = 101
    INSERT = 20
    DELETE = 0

    예상 최종 = 121

정상이다.

이 계산이 맞지 않으면 apply 전에 원인을 확인한다.


### 9.24 개발 DB 실제 반영

Dry-run 결과가 모두 예상과 일치하면 같은 명령에:

    --apply

를 추가한다.

예:

    python scripts/import_curriculum_postgres.py \
      data/seed/curriculum_2022.csv \
      --project-ref rkunrjwetsnonwnmatec \
      --replace \
      --apply


### 9.25 Apply 출력

정상 적용되면 마지막에 다음과 같은 결과가 나온다.

    2022학번 PostgreSQL import 완료
    최종 행: 121개

Importer는 동기화 후 실제 DB의 cohort 행 수가 seed 행 수와 같은지도 확인한다.

예상과 다르면 오류를 발생시킨다.


### 9.26 Apply가 곧 검증 완료를 의미하지 않는다

Importer가 성공했다고 바로 개발 DB 검증을 끝내지 않는다.

실제 SQL로 최소한 다음을 다시 확인한다.

- total
- current
- legacy
- attribute change count
- 주요 변경 과목


### 9.27 개발 DB 기본 행 수 검증

PostgreSQL에서:

    SELECT
        COUNT(*) AS total_rows,
        COUNT(*) FILTER (
            WHERE change_role = 'current'
        ) AS current_rows,
        COUNT(*) FILTER (
            WHERE change_role = 'legacy'
        ) AS legacy_rows
    FROM public.curriculum_courses
    WHERE entry_year = 2022;

예상값과 정확히 일치하는지 확인한다.


### 9.28 Attribute Change 개수 검증

    SELECT COUNT(*) AS attribute_change_count
    FROM public.curriculum_courses
    WHERE entry_year = 2022
      AND change_role = 'current'
      AND (
          previous_credits IS NOT NULL
          OR previous_completion_type IS NOT NULL
          OR previous_grade IS NOT NULL
          OR previous_semester IS NOT NULL
      );

SQLite에서 확인한 값과 같아야 한다.


### 9.29 구조변경 그룹 검증

필요하면 다음 쿼리로 확인한다.

    SELECT
        change_group,
        change_type,
        change_role,
        course_code,
        course_name,
        grade,
        semester,
        completion_type,
        credits,
        change_effective_year
    FROM public.curriculum_courses
    WHERE entry_year = 2022
      AND change_group IS NOT NULL
    ORDER BY
        change_group,
        change_role,
        course_code;

특히 새로 추가한 구조변경 그룹이 PostgreSQL에서도 legacy/current 형태로 정확히 들어갔는지 확인한다.


### 9.30 주요 과목 Spot Check

대규모 수정에서는 대표적인 과목 몇 개를 직접 확인한다.

예:

    SELECT
        course_code,
        course_name,
        grade,
        semester,
        completion_type,
        credits
    FROM public.curriculum_courses
    WHERE entry_year = 2022
      AND course_code IN (
          'ADA115',
          'ADA148',
          'ADA198',
          'ADA217',
          'ADA237',
          'ADB103',
          'ADB111',
          'ADB113'
      )
    ORDER BY course_code;

실제 검증 대상 코드는 해당 작업에서 중요한 과목들로 바꾼다.


### 9.31 ID 보존 직접 검증

필요하면 업데이트 전후 특정 과목의 ID를 직접 비교할 수 있다.

Import 전:

    SELECT id, course_code, course_name
    FROM public.curriculum_courses
    WHERE entry_year = 2022
      AND course_code = 'ADB046';

Import 후 같은 쿼리를 실행한다.

기존 행이 UPDATE 대상으로 매칭되었다면 ID가 유지되어야 한다.


### 9.32 사용자 기록 FK 확인

대규모 구조변경 후에는 필요하면 orphan 여부를 확인한다.

    SELECT COUNT(*) AS remaining_orphans
    FROM public.user_course_records AS ucr
    LEFT JOIN public.curriculum_courses AS cc
      ON cc.id = ucr.curriculum_course_id
    WHERE ucr.curriculum_course_id IS NOT NULL
      AND cc.id IS NULL;

정상 결과:

    0

이어야 한다.


### 9.33 FK 자체 확인

필요한 경우 현재 FK 정의도 확인할 수 있다.

    SELECT
        conname,
        pg_get_constraintdef(oid)
    FROM pg_constraint
    WHERE conrelid =
        'public.user_course_records'::regclass
      AND conname =
        'user_course_records_curriculum_course_fk';

현재 구조에서 `curriculum_course_id`가 `curriculum_courses(id)`를 참조하고 있는지 확인한다.


### 9.34 개발 웹 확인

DB SQL 검증이 끝나면 개발 환경 웹에서도 대상 학번을 확인한다.

주요 확인 대상:

- 현재 교육과정 탭
- 변경사항 탭
- current 과목 위치
- legacy → current 표시
- 속성변경 전/후 표시
- 전필/전선
- 학점
- 학년/학기
- 변경 개수

DB 값이 맞더라도 frontend의 reconstruction 로직이 잘못되면 화면에서는 다르게 보일 수 있다.


### 9.35 변경사항 화면에서 확인할 것

구조변경:

    legacy
        ↓
    current

관계가 올바르게 렌더링되는지 본다.

속성변경:

    이전 값
        ↓
    현재 값

이 올바르게 표시되는지 확인한다.

예:

    2학점 → 3학점
    전선 → 전필
    4-1 → 4-2

등이다.


### 9.36 개발 DB에서 문제가 발견된 경우

개발 DB 적용 후 문제가 보이면 운영 DB로 넘어가지 않는다.

수정 순서:

    seed 수정
        ↓
    audit
        ↓
    SQLite import
        ↓
    SQLite 검증
        ↓
    Git dev 수정
        ↓
    개발 PostgreSQL dry-run
        ↓
    apply
        ↓
    재검증

DB에서 직접 값을 수정해 임시로 맞추는 방식은 피한다.

기준 source인 seed부터 다시 수정한다.


### 9.37 PostgreSQL에서 직접 UPDATE하는 것을 피하는 이유

예를 들어 개발 DB에서:

    UPDATE curriculum_courses
    SET credits = 3
    WHERE ...

를 직접 실행하면 당장은 화면이 맞을 수 있다.

하지만 seed에는 이전 값이 남아 있으므로 다음 importer 실행 때 다시 덮어써진다.

따라서 정상적인 데이터 흐름은 항상:

    Seed
        ↓
    Importer
        ↓
    PostgreSQL

이다.


### 9.38 실제 2022학번 개발 DB 예시

2022학번의 개발 DB dry-run에서는 다음 결과가 나왔다.

    DB 기존 2022학번 행: 101개

    UPDATE: 101개
    INSERT: 20개
    DELETE: 0개

이는 기존 101개의 ID를 모두 보존하고, 신규 20개 행만 INSERT하는 계획이었다.

Apply 후:

    최종 행: 121개

가 확인되었다.

추가 SQL 검증:

    total_rows = 121
    current_rows = 105
    legacy_rows = 16
    attribute_change_count = 11

도 seed 및 SQLite와 일치하였다.


### 9.39 개발 DB 완료 기준

다음 조건을 만족해야 운영 DB 단계로 넘어간다.

- 접속 대상이 개발 Supabase임
- dry-run 완료
- UPDATE 수가 설명 가능함
- INSERT 수가 설명 가능함
- DELETE 수가 설명 가능함
- 예상하지 못한 사용자 참조 삭제 없음
- apply 성공
- 최종 행 수가 seed와 일치
- current / legacy 수가 SQLite와 일치
- attribute change 수가 SQLite와 일치
- 주요 구조변경 값 정상
- orphan 없음
- 개발 웹 렌더링 정상


### 9.40 개발 DB 단계에서의 Stop 조건

다음 중 하나라도 발생하면 운영 DB로 진행하지 않는다.

    잘못된 project ref
    예상하지 못한 DELETE
    사용자 기록이 DELETE 후보를 참조
    최종 행 수 불일치
    current / legacy 불일치
    attribute change 불일치
    주요 과목 값 불일치
    개발 웹 변경내역 오류


### 9.41 다음 단계

개발 PostgreSQL과 개발 웹까지 정상이라면 다음 단계는 운영 DB 반영이다.

순서:

    운영 PostgreSQL dry-run
        ↓
    개발 DB 결과와 비교
        ↓
    운영 apply
        ↓
    운영 SQL 최종 검증

운영 DB에서도 dry-run을 생략하지 않는다.


### 9.42 핵심 원칙

개발 PostgreSQL 단계의 핵심은 다음과 같다.

> 기존 사용자 기록과 연결된 curriculum ID를 가능한 한 유지하면서, Git에 확정된 seed와 개발 DB를 안전하게 동기화한다.

그리고 반드시:

    dry-run
        ↓
    계획 검토
        ↓
    apply
        ↓
    SQL 검증
        ↓
    웹 확인

순서를 지킨다.
